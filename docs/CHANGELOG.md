# Changelog

## Unreleased

### Upgrading from 0.1.0

Nothing exported by 0.1.0 was removed or changed in its signature (checked with `apidiff`, which every push now runs against the last release). What can still surprise code written for 0.1.0:

- `Animated()` returns an error wrapping `errors.ErrUnsupported` for an animation it cannot keep (an animated GIF, WebP or PNG to JPEG, BMP or TIFF), where 0.1.0 silently wrote the first frame; to PNG it writes an APNG. Leave out `Animated()` to get the first frame.
- A lossy WebP is decoded to `*image.NRGBA` strips, no longer to `*image.YCbCr`, so that its colours are libwebp's; `Metadata()` still reports `ycbcr`. Code that type-asserts the decoded image should accept any `image.Image`.
- `Frames().LoopCount` of a GIF is the number of times it plays, as documented, one more than 0.1.0 returned.
- The default PNG level is 7 with Go 1.27 (6 before): smaller files, written more slowly. `PNGOptions{CompressionLevel: 6}` keeps the old files.
- `Threads(n)` is no longer capped at 3: a larger n uses that many cores.
- JPEG files are written as libjpeg-turbo writes them (Pillow's and sharp's bytes), no longer as `image/jpeg` does: at the same quality, pixels a level or so apart, files of about the same size.
- `Flatten` of an image whose colours are not multiplied by alpha (a PNG, a WebP; most images), and JPEG output of an image with transparency (flattened over black), take the colours as libvips does, `(colour×alpha + background×(255−alpha)) / 255` with the fraction dropped, so that they are sharp's to the byte; they were a level apart on some pixels.
- A CMYK file (JPEG, TIFF) without a colour profile is converted to sRGB through libvips's CMYK profile, as libvips and sharp convert it, no longer with `color.CMYK`'s plain formula: printing inks come out as printed (full cyan is RGB 0,153,228, no longer 0,255,255). A `*image.CMYK` given to `FromImage` keeps `color.CMYK`'s values.

### Added

- Image adjustments: `Grayscale`, `Modulate`, `Blur`, `Sharpen` (mild sharpening or unsharp masking), `Extend`, `Trim` and `RotateBy` (arbitrary angle, sharp's `rotate` to the byte).
- `inspect.Stats`, `inspect.Hash` (perceptual hash) and `inspect.ReadExif` / `ParseExif`; the `stats`, `hash` and `exif` commands. `Stats` also reports what sharp's `stats()` does, to the last digits: `Channels` (type `ChannelStats`), `Entropy` and `Sharpness`.
- Operations by name: `RegisterOperation`, `UnregisterOperation`, `LookupOperation`, `Operations` and `Image.Do`. Hooks around every step: `Image.Around`. `ParseColor`.
- Package `cli`: the command line as a library (`cli.Main`, `cli.Run`), allowing programs to add their own operations; the `-op NAME[:ARGS]` flag and the `ops` command.
- `ToSRGB()` / `-srgb`: converts colours to sRGB using the colour profile. GIF and BMP output, which cannot carry a profile, is converted automatically.
- Grey colour profiles (a tone curve, as Photoshop's dot gain profiles) are converted, the image staying grey. Colour profiles of lookup tables (lut8, lut16, lutAToB; RGB and CMYK, to Lab or XYZ) are converted, by their perceptual table, interpolated as LittleCMS does (within 1 level of its perceptual conversion for a CMYK printing profile), the black point compensated as LittleCMS compensates it. A CMYK JPEG with a profile is turned into sRGB through it as it is decoded, as sharp does (it was converted with the plain formula, its profile written to the RGB output).
- Colour profiles in WebP and TIFF files (read and write); EXIF in WebP files.
- `JPEGOptions.Trellis` / `-jpeg-trellis`: trellis quantization, following mozjpeg.
- `JPEGOptions.QuantTable` (type `QuantTable`, with a named constant for each choice) / `-jpeg-quant-table`: mozjpeg's nine quantization tables, numbered as its `-quant-table`; `QuantTableStandard` (0), the default, is the JPEG standard's.
- `QuantTableJpegli` (`-jpeg-quant-table 9`): JPEG quantization tables made as jpegli makes them, with its dead zone without `Trellis`; with `Progressive` and `Trellis`, 15% smaller than mozjpeg's defaults at equal SSIMULACRA2.
- `-webp-effort`: the effort of WebP on the command line (`WebPOptions.Effort` in the library).
- `GIFOptions.Lossy` / `-gif-lossy`: lossy LZW compression for GIF, still and animated (the method of gifsicle's `--lossy`): a photographic animation 18% smaller at 16, 32% at 24.
- Animated GIF: frames with more than 256 colours together but at most 256 each are written with a palette per frame, every pixel unchanged (they were reduced to one palette, which changed pixels and made the file larger); a frame of changes is written whichever of three ways codes smallest, and its LZW dictionary kept when full while that pays: 0.2–0.45% smaller than gifsicle `-O3` on three animations.
- Animated WebP output: `Animated()` with WebP output writes an animated GIF as an animated WebP (lossy or lossless), storing only the rectangle that changed in each frame.
- Animated WebP input: read as its first frame (previously rejected as an unreadable image), and with `Animated()` frame by frame into an animated GIF or WebP: each frame is drawn on the picture as libwebp's animation decoder draws it (blended or put as it is, its rectangle cleared afterwards or not), pixel for pixel; how long the frames show and how often the animation plays carry over (to a GIF in hundredths of a second, and as repeats after the first time). `Frames` counts the frames of animated WebP and PNG (APNG) files; `info` shows them.
- Animated PNG (APNG) input: with `Animated()`, frame by frame into an animated GIF or WebP, each frame drawn as the APNG specification says (put as it is or composited over, as apngdis does; cleared, put back or left afterwards), checked frame by frame against a renderer written from the specification.
- Animated PNG (APNG) output: `Animated()` with PNG output writes an APNG, without loss: one palette for all frames when they have 256 colours or fewer (else RGB or RGBA), later frames as the rectangle that differs from what they are drawn on (the frame before kept, cleared or undone, as apngopt chooses), as it is or blended over with the unchanged pixels transparent, whichever is smallest; frames alike merged. Pillow reads them back pixel for pixel; an animated GIF of a moving ball becomes 30% smaller, and photographic animations Pillow wrote as APNG 0.1% and 18% smaller.
- `CompositeOptions.WidthRatio` / `HeightRatio`: watermark size as a fraction of the base image; `-watermark-width N%`.
- Lossy WebP: segments with individual quantizers (spatial noise shaping, ported from libwebp).
- `pipeline.Env.SetHelpers`, `Helpers`, `Parallel` and `Go`, allowing stages to distribute their work across cores.
- TIFF output: `TIFFLZW` compression (as libtiff writes it) and `TIFFOptions.Predictor` (horizontal differencing, sharp's default): a 24-megapixel photograph as LZW 82 → 52MB, as Deflate 67 → 45MB; `-tiff-compression lzw`, `-tiff-predictor`.
- `SharpenOptions.Method` `SharpenLibvips` with `SharpenOptions.Curve` (`SharpenCurve`, `DefaultSharpenCurve()`): sharp's `sharpen` with a sigma, on the lightness alone (within a level on a few pixels); by name `sharpen SIGMA,libvips[,FLAT,JAGGED,JAGGED_FROM,MAX_BRIGHTEN,MAX_DARKEN]`, and the same for `-sharpen`.
- `Affine(a, b, c, d, AffineOptions{...})`: sharp's `affine` to the byte (bilinear, nearest and bicubic `Interpolator`s, with and without transparency); by name `affine A,B,C,D[,BACKGROUND[,IDX,IDY,ODX,ODY]][,bilinear|nearest|bicubic]`.
- `EnsureAlpha` (sharp's `ensureAlpha`, to the byte); by name `ensure-alpha [ALPHA]`.
- Resize kernels `KernelMKS2013` and `KernelMKS2021` (Magic Kernel Sharp, as sharp's `mks2013` and `mks2021`); `-kernel mks2013|mks2021`.
- `Rank` (Pillow's `RankFilter`, `MinFilter`, `MaxFilter`), `Dilate` and `Erode` (sharp's `dilate` and `erode`), all to the byte; by name `rank SIZE,RANK`, `dilate [WIDTH]`, `erode [WIDTH]`. Dilate and erode take a time that hardly grows with the width (libvips' grows with its square).
- `BlurOptions` (`Method`: `BlurPillow`, Pillow's, the default, or `BlurLibvips`, sharp's `blur` to the byte, transparency included; `MinAmplitude`, sharp's `minAmplitude`); by name `blur SIGMA,libvips[,MIN_AMPLITUDE]`; `-blur-method`, `-blur-min-amplitude`. The kernel is worked out as at most 20 nested boxes, so its time hardly grows with sigma.
- Options after sharp's: `NegateOptions.Alpha` (negate the transparency too, sharp's default), `ThresholdOptions.PerChannel` (sharp's `greyscale: false`), `ModulateOptions.Lightness` (sharp's `lightness`) and `GrayscaleOptions.Linear` (sharp's `greyscale`, to the byte); by name `negate alpha`, `threshold LEVEL,channels`, `modulate B,S,H,L`, `grayscale linear`; `-grayscale-linear` and a fourth number for `-modulate`.
- XMP: `KeepXmp()` / `-keep-xmp` keeps the XMP packet in JPEG, PNG, WebP and TIFF output; `Info.HasXmp`, `inspect.ReadXmp`; `EncodeOptions.Xmp` and `pipeline.Meta.Xmp` for formats of one's own. Read and written as sharp does (checked both ways on files sharp wrote).
- `Trim` finds the edges as sharp's `trim` does (libvips' `find_trim`): on a 3×3 median of the image, so that noise and specks do not stop it (the same boxes as sharp on the same pixels); `TrimOptions` gives it a `Background`, `LineArt` (no median, for drawings of thin lines) and a `Margin`; `-trim-background`, `-trim-line-art`, `-trim-margin`.
- `JPEGOptions.ChromaSubsampling` (type `ChromaSubsampling`: `Chroma420`, the default, `Chroma422`, `Chroma444`) / `-jpeg-chroma`: JPEG output with colour at full resolution or half the width, plain, optimized, progressive and with the trellis (sharp's `chromaSubsampling`).
- TIFF files with JPEG compression (compression 7: libtiff's, the default of libvips and sharp) are read, in strips and in tiles, colour and grey.
- Resolution: `Info.Density` (pixels per inch, read from JFIF, EXIF, pHYs, TIFF and BMP), kept in the output by default, `Density(dpi)` / `-density` to set it; `EncodeOptions.Density` and `pipeline.Meta.Density` for formats of one's own. `info` prints it.
- `ExtendWith` (type `ExtendMode`: `ExtendCopy`, `ExtendRepeat`, `ExtendMirror`) / `-extend-with`: borders made of the image, pixel for pixel sharp's `extend` with `extendWith`; `Do("extend")` takes copy, repeat or mirror in place of the colour.
- `Filter` (type `ImageFilter`): Pillow's built-in filters (blur, contour, detail, edge enhance, emboss, find edges, sharpen, smooth), and `Convolution.Method` `ConvolvePillow`: its `ImageFilter.Kernel`, to the byte; by name `filter NAME` and `convolve …,pillow`.
- `BoxBlur(radius)` (`boxblur`): Pillow's `ImageFilter.BoxBlur`, to the byte, fractional radii included.
- `RotateOptions` for `RotateBy` (`Method`: `RotateLibvips`, sharp's, or `RotatePillow`, Pillow's `Image.rotate` to the byte; `Interpolator`; `Expand`); by name `rotate DEGREES[,BACKGROUND][,pillow][,nearest|bilinear|bicubic][,expand]`.
- `ToTiles(path, TileOptions)`: a pyramid of tiles, as sharp's `tile` (libvips' `dzsave`) writes it, every JPEG tile and the files that describe them to the byte, images with transparency included: Deep Zoom (`.dzi`), Google Maps (`TileGoogle`, with `blank.png`), IIIF Image API 2 and 3 (`TileIIIF`, `TileIIIF3`, with `info.json`) and Zoomify (`TileZoomify`); `TileOptions.Depth` (`TileDepth`), `Background`, `Center`, `SkipBlanks` and `ID` as sharp's `depth`, `background`, `centre`, `skipBlanks` and `id`; in a ZIP archive for a path ending in `.zip`, or to any writer with `ToTilesWriter`, as sharp's `zip` container; streamed, the tiles encoded on the helpers; also `ToFile("x.dzi")` and, on the command line, an output named `.dzi` with `-tile-size`, `-tile-overlap` and `-tile-layout`.
- The Porter-Duff blend modes of sharp's composite, and add and saturate: `BlendClear` to `BlendXor`, `BlendAdd`, `BlendSaturate` (`BlendDestIn` with a mask keeps the image where the mask is opaque); also for `-watermark-blend`.
- Module `github.com/whhhh1500/goimgtools/heic`: HEIC read and written with gen2brain/h265, an HEVC codec in pure Go (its decoding that of the conformance suite; SIMD, or none with `-tags noasm`, the same pixels): grids, transparency, irot/imir/clap (the EXIF orientation then set to 1), EXIF, XMP and the colour profile read (a Display P3 profile for an nclx box saying so) and written; `heic.Options{Quality, Effort, Lossless, Chroma444}`, MaxFileSize by its quality.
- Module `github.com/whhhh1500/goimgtools/avif`: AVIF read and written (libavif with dav1d and aom, compiled to WebAssembly, through gen2brain/avif; no cgo), registered when imported; `avif.Options{Quality, Effort, Lossless, Chroma444}`, MaxFileSize by its quality; irot and imir turn the image upright.
- TIFF output with Deflate or LZW: the strips are compressed on the other cores (`Threads(4)` and more), the file the same; a 6000×4000 photograph as Deflate in 0.49s with 8 threads instead of 1.73s.
- `Curves(points, CurvesOptions)`: tone curves, a monotone cubic through the points, for all colour channels and for each; by name `curves`.
- A grey image made coloured (a coloured overlay, `Tint`) no longer keeps its grey colour profile, which colour pixels cannot carry: each channel is taken through the profile's curve to sRGB.
- EXIF in TIFF files: read from the first directory and the EXIF and GPS directories it points to (so `Rotate()` turns a TIFF by its orientation, as Pillow's `exif_transpose` and sharp do, and `KeepExif` and `inspect.ReadExif` see it), and written there with `KeepExif`; Pillow reads the written tags back unchanged.
- JPEG decoding with `Threads(5)` or more: the inverse DCTs of a sequential JPEG are made on the other cores while the next row of blocks is decoded; a 6000×4000 JPEG decodes in 122–142ms instead of 172ms (pixels unchanged).
- Animated GIF output: a frame that changes nothing lengthens the frame before instead of being written (up to 655.35s), as in WebP and APNG output.
- `MaxFileSize` for PNG and GIF: the most colours that fit (a PNG first without loss); `-max-size` likewise.
- `Transform(width, height, t, TransformOptions)`: Pillow's `Image.transform` to the byte, with `TransformAffine`, `TransformExtent`, `TransformPerspective` and `TransformQuad`, and `TransformPerspectiveQuad` (the perspective that takes the output's corners to four points, worked out from them); by name `transform WIDTH,HEIGHT,KIND,NUMBERS...[,INTERPOLATOR][,BACKGROUND]`.
- Pillow's `ImageOps` and `ImageEnhance`, to the byte: `Posterize`, `Solarize`, `Equalize`, `AutoContrast` (`AutoContrastOptions`) and `Enhance` (type `Enhancement`: `EnhanceColor`, `EnhanceContrast`, `EnhanceBrightness`, `EnhanceSharpness`); by name posterize, solarize, equalize, autocontrast, enhance.
- `ResizeOptions.Method` (type `ResizeMethod`) / `-resize-method`: `ResizeLibvips` is sharp's `resize`, to the byte, for every kernel, fit, position and background, JPEGs shrunk on load included and, with `FastShrinkOnLoad`, WebPs scaled on load as libwebp scales them (checked against sharp on 578 resizes); `ResizePillow` is Pillow's `Image.resize`, to the byte (checked on 346 resizes), its fits those of `ImageOps` (`contain`, `cover`, `pad`, `fit`), and with `ResizeOptions.ReducingGap` (`-reducing-gap`) its `reducing_gap` and `Image.thumbnail`; `ResizeDraw`, the default, works as before. `Do("resize")` takes `draw`, `libvips` or `pillow` as a seventh word. `KernelBox` and `KernelHamming` (`-kernel box`, `hamming`): Pillow's `BOX` and `HAMMING`.
- `ResizeOptions.LinearLight` / `-linear-light`: resizing in linear light, as libvips' `thumbnail` with `linear`; `Do("resize")` takes `linear` as a sixth word.
- `ResizeOptions.Position` (the part `FitCover` keeps, where `FitContain` puts the image) and `ResizeOptions.Interesting` (type `Interesting`: `InterestingEntropy`, `InterestingAttention`, as sharp's smart crop strategies) / `-position`. `Do("resize")` takes them as a fifth word.
- `Recomb`, `Unflatten`, `ExtractChannel` (type `Channel`) and `RemoveAlpha`, after sharp's `recomb`, `unflatten`, `extractChannel` and `removeAlpha` (the first two byte-for-byte identical), and by name: recomb, unflatten, extract-channel, remove-alpha.
- `CompositeOptions.Blend` (type `BlendMode`) / `-watermark-blend`: the blend modes of sharp's composite (multiply, screen, overlay, darken, lighten, colour dodge and burn, hard and soft light, difference, exclusion), within a level of sharp's results.
- Levels and filters after sharp: `Negate`, `Linear`, `Gamma`, `Threshold`, `Tint`, `Normalize` (`NormalizeOptions`), `CLAHE` (`CLAHEOptions`), `Median` and `Convolve` (`Convolution`), and by name (`Do`, `-op`): negate, linear, gamma, threshold, tint, normalize, clahe, median, convolve. `Negate`, `Linear`, `Threshold`, `CLAHE`, `Median` and `Convolve` give sharp's results to the byte, `Normalize` and `Tint` within a level; `Median` is also Pillow's `MedianFilter` to the byte.

### Changed

- JPEG files are written as libjpeg-turbo writes them, to the byte (sharp's files as they are, Pillow's without their JFIF segment): libjpeg's colour conversion, downsampling, accurate integer forward DCT, dummy blocks past the edges, optimized Huffman tables and markers, at the same speed. A resolution is written as JFIF 1.01, as libjpeg writes it.
- `FastShrinkOnLoad` applies to a lossy WebP without alpha too: reduced to a third or less, it is decoded at twice the size of the result, as libwebp scales while decoding, and the kernel does the rest (a 6000×4000 one to fit 400×400 in 0.39s instead of 0.74s, 48–51dB from the result without the option).
- `FastShrinkOnLoad` reduces the blocks with libjpeg's reduced inverse DCTs (`jidctred.c`) instead of averages worked out afresh, at the same speed: the planes of a 4:4:4 or grey JPEG are those of libjpeg's scaled decoding (Pillow's `draft`), and the result as close to a resize of the full image (46.7–50.5dB).
- JPEG files are decoded as libjpeg-turbo decodes them, and so Pillow and sharp, to the byte (its accurate integer inverse DCT, its fancy upsampling of subsampled chroma, its YCbCr to RGB tables), instead of as `image/jpeg` does: subsampled colour edges are smoother (a 4:2:2 photograph 0.36 dB closer to the original), and every operation that gives Pillow's or sharp's pixels does so on JPEG input too. Colour JPEG strips are RGBA rather than YCbCr, but where a JPEG goes straight into a JPEG or lossy WebP file.
- TIFF decoding: LZW 1.5 times faster (a 6000×4000 RGBA image in 0.45s instead of 0.68s; libtiff 0.31s), with the same bytes and errors as `x/image` on any input (fuzzed), and Deflate blocks read 64KB at a time (0.26s instead of 0.30s; libtiff 0.27s).
- `FitCover` puts a centred crop where sharp does: when the image is an odd number of pixels larger than the box, the odd pixel is cut on the left (top) rather than the right (bottom).
- JPEG encoding: the SIMD kernels write the quantized coefficients in zig-zag order themselves, and the mask of the nonzero ones is taken with AVX2: a 6000×4000 photograph at quality 85 in 87ms instead of 100ms on one core, with optimized tables 151ms instead of 168ms.
- Lossy WebP encoding: the 4x4 forward transform (after libwebp's FTransform_SSE2), the inverse transform, the quantization and the squared error of the mode search, and the histogram of coefficients of the analysis, run with AVX2 or NEON; the trellis keeps the two nodes of each coefficient in registers with the path to each as a bit mask, and counts the bits of the block as it goes; the bits of a block are summed without branches. Every number is that of the Go code, so the files are the same: a 6000×4000 photograph at quality 80 in 4.4s instead of 6.5s on one core at the default effort, 2.6s instead of 4.0s at effort 1.
- `Resize` with the default method keeps 16-bit samples: a 16-bit PNG or TIFF is scaled to 16-bit strips (`*image.RGBA64`, `*image.Gray16`), the values `x/image`'s `Scale` gives such a destination, and written as 16 bits; it was cut to 8 bits.
- PNG encoding: the five filters of each row (and the sums by which libpng's heuristic chooses one) are worked out with AVX2 or NEON, the same row and choice as before: a 6000×4000 photograph to PNG (level 7) in 1.43s instead of 1.73s on one core.
- NEON on arm64 (with Go 1.27 or later; the `purego` build tag leaves it out): every AVX2 kernel (JPEG decoding and encoding, lossy WebP decoding, the search of loop filter levels, `ResizeLibvips`' reduce) has a NEON version, every byte that of the Go code.
- Lossy WebP at effort 3 weighs the 4x4 modes without the trellis and keeps it for the mode chosen (libwebp's method 5): 15% faster than effort 4, which it was the same as, for files about 1% larger at the same SSIMULACRA2 and butteraugli (14 images).
- Lossy WebP encoding with AVX2 (amd64; the `purego` build tag leaves it out): the search of loop filter levels filters each macroblock with the decoder's AVX2 loop filter and takes the SSIM sums of its windows with AVX2, every number that of the Go code, so the files are the same: a 6000×4000 photograph at quality 80 in 6.5s instead of 8.3s on one core.
- Resizing with AVX2 (amd64; the `purego` build tag leaves it out): `ResizeLibvips`'s reduce down and across, and libjpeg's 4×4 inverse DCT of a JPEG shrunk on load, run as assembly, every byte that of the Go code (and so sharp's); NRGBA strips of an image without transparency are encoded as JPEG through the same conversion as RGBA. A 6000×4000 JPEG fitted into 1536×1536 (Lanczos 3, `FastShrinkOnLoad`) and written as a JPEG: 109ms instead of 196ms on one core (sharp: 92ms).
- JPEG encoding with AVX2 (amd64; the `purego` build tag leaves it out): the conversion of RGB to YCbCr, the downsampling of the chroma, the forward DCT and the quantization run as assembly, every byte that of the Go code; and the first pass of optimized Huffman tables stages the symbols (a byte each) instead of a scan coded with the standard tables, which the second pass had to decode. A 6000×4000 photograph at quality 85: 100ms instead of 213ms on one core (libjpeg-turbo through Pillow: 66ms); with optimized tables 168ms instead of 388ms (167ms).
- JPEG decoding with AVX2 (amd64; the `purego` build tag leaves it out): the inverse DCT and the conversion of colour, with the upsampling of the chroma, run as assembly after libjpeg-turbo's SIMD code, every byte that of the Go code: a 6000×4000 photograph (quality 90) decodes on one core in 99ms (4:2:0), 109ms (4:2:2) and 126ms (4:4:4) instead of 208, 226 and 250ms, as fast as libjpeg-turbo with its SIMD (through Pillow: 101, 110 and 121ms).
- JPEG decoding is 45% faster, with the same pixels: the entropy-coded data is read 64 bits at a time and decoded through 11-bit tables that give most coefficients' values together with their codes, coefficients are dequantized as they are decoded, and the inverse DCT skips rows of zeros (a 6000×4000 baseline photograph in 98ms instead of 188ms on one core). With `FastShrinkOnLoad` the image is decoded straight to 1/2, 1/4 or 1/8 of its size from the coefficients, as libjpeg does, instead of being decoded in full and averaged, and the rest of the resize scales its Y, Cb and Cr planes as they are, in fixed point, instead of converting to RGBA: shrinking that photograph to fit 400×400 takes 82ms instead of 231ms (libvips' `vipsthumbnail`: 97ms), and to fit 1536×1536 157ms instead of 320ms (148ms; with 2 threads 108ms against its 172ms).
- A progressive JPEG read from a file or from memory is decoded with its scans in step, a row of blocks at a time, instead of storing the coefficients of the whole image (72MB at 6000×4000, which went to a temporary file under the default limit), and refinement scans visit only the coefficients that are not zero: a 6000×4000 photograph is decoded about three times as fast (0.24s instead of 0.70s on one core), with no temporary file and 0.5MB more memory. Shrunk by 8 with `FastShrinkOnLoad`, where each block becomes the mean of its pixels, only the scans of DC coefficients are decoded: that photograph shrunk to fit 400×400 in 50ms instead of 745ms (libvips' `vipsthumbnail`: 228ms). An end-of-band run that a corrupt scan leaves unfinished now ends with the scan, as in libjpeg; the standard library carries it into the next scan.
- JPEG encoding is more than twice as fast, writing the same bytes as before (those of the standard library's `jpeg.Encode`): the entropy-coded data is gathered 64 bits at a time and written 32 at a time, a block's bits kept in registers; only the coefficients that are not zero are visited, found four at a time; quantization has no branch; the colour conversion of RGBA and NRGBA pixels is done inline; and the chroma of a YCbCr image subsampled 4:2:0 (as decoded JPEGs mostly are) is taken as it is instead of being spread over every pixel and averaged back (4:4:4: averaged straight from its planes). A 6000×4000 JPEG re-encoded on one core: 0.23s instead of 0.54s (libvips: 0.12s; with 2 threads 0.13s against its 0.13s, with 4 threads 0.10s).
- PNG images and Deflate-compressed TIFF images are decompressed about twice as fast (`internal/inflate`, written with libdeflate's method: a 64-bit bit buffer refilled without a branch, tables that give a code's extra bits with it, the next code looked up before the refill, matches copied eight bytes at a time), accepting and rejecting the same data as before and reading as much of the file. A 6000×4000 RGB PNG is decoded in 0.25s instead of 0.37s on one core (libvips: 0.25s); converted to JPEG, 0.39s instead of 0.51s (0.25s).
- PNG rows filtered with Paeth are undone with the channels of a pixel together and without branches (the standard library undoes one channel along the row, then the next): a 6000×4000 RGBA photograph shrunk to fit 1536×1536 in 0.45s instead of 0.51s on one core, 0.26s instead of 0.32s with 2 threads (vipsthumbnail: 0.43s).
- Lossy WebP encoding at the default effort is 25% faster, writing the same files: the coded tokens kept between the two passes are read back as libwebp's bit reader reads (56 bits at a time), the SSIM sums by which the loop filter levels are chosen are taken over the fixed 16×16 and 8×8 blocks directly, and the trellis looks its cost tables up once per coefficient. A 6000×4000 photograph: 7.5s instead of 10.1s on one core, 1.55s instead of 1.79s with 8 threads.
- Lossy WebP decoding with AVX2 (amd64; the `purego` build tag leaves it out): the loop filter, and the upsampling and conversion of colour, run as assembly after libwebp's SSE2 code, every byte that of the Go code: a 6000×4000 photograph decodes on one core in 0.36s instead of 0.57s, faster than libwebp 1.6 with its SIMD (0.50s through Pillow).
- Lossy WebP decoding is 15–18% faster, with the same pixels: the bits are read as libwebp's VP8GetBit reads them, and a block's coefficients with the reader held in local variables (a 6000×4000 image at quality 95: 0.78s instead of 0.95s; dwebp 0.48s).
- Lossy WebP decoding shares its work when there are cores for it (`Threads` of 4 or more): the loop filter of each row of macroblocks runs while the next row is decoded, as libwebp's threaded decoder does, and the conversion to RGB is shared out; the pixels are the same. A 6000×4000 photograph shrunk to fit 1536×1536 in 0.49s instead of 0.57s with 4 threads.
- Lossless WebP decoding (and the compressed alpha of lossy WebP) takes 25–65% less time, with the same pixels and the same failures as `golang.org/x/image/webp`: the Huffman codes are decoded through tables, as libwebp decodes them (a code that is not complete keeps the tree), 64 bits of input at a time, and the predictor transform works on a run of pixels four channels at a time (a 1600×1097 photograph in 31ms instead of 42ms on one core, a 1001×687 one in 15ms instead of 22ms; libwebp's `dwebp`: 30ms and 13ms, 25ms and 11ms with its SIMD).
- A YCbCr or NYCbCrA image with chroma subsampled vertically and its top edge above 0 at an odd row no longer makes JPEG encoding (or anything that re-cuts it into bands) fail with an internal error.
- From level 7, PNG output tries no filter against the filters the rows choose, every 32KB of rows, and keeps the smaller: screenshots, icons and drawings 10–19% smaller; photographs unchanged.
- PNG levels 8 and 9 search for the smallest file: rows are filtered as oxipng's Brute strategy filters them (every filter tried), and the data is compressed with a Go port of libdeflate's near-optimal parsing instead of `compress/flate`, its blocks split by cost and its symbols priced at their entropy, as zopfli does. On 17 screenshots, photographs and game artwork, 14.2% (8) and 15.5% (9) smaller than level 7, against 14.8% for oxipng `-o max` (in a sixth of its time) and 15.8% for ECT `-9`; the same file with every Go version. They take about 4MB (8) and 6.5MB (9) more memory per thread.
- The minimum Go version is 1.26 (0.1.0 required 1.27). PNG files written with Go 1.26 and Go 1.27 differ in their bytes but not in their pixels, as Go 1.27 rewrote `compress/flate`. With Go 1.26 the default PNG level is 6 (see below).
- Progressive JPEG chooses its scans as mozjpeg does (`optimize_scans`): files 0.4–14% smaller (2.4% on average over 18 images, 3.9% with `Trellis` and `QuantTable: QuantTableImageMagick`; with both, 0.7% smaller than mozjpeg's defaults at equal PSNR), with the same pixels. Single-threaded it takes 3–19% longer; the candidate scans are counted in parallel with `Threads`.
- `Animated()` no longer ignores an animation it cannot keep: an animated GIF, WebP or PNG to an output format other than GIF and WebP returns an error wrapping `errors.ErrUnsupported` instead of writing the first frame. A still image passes as before. So does `MaxFileSize` with `Animated()` on an animation, which was ignored.
- `Threads(n)` now extends to the number of CPUs (previously capped at 3). From 4 threads upwards, resizing, blurring, sharpening, modulation, rotation, and JPEG, PNG and lossy WebP encoding distribute their work across cores. Output is byte-for-byte identical for any number of threads.
- The default PNG compression level is now 7 with Go 1.27 (previously 6, the standard library's default; with Go 1.26 it stays 6, where level 7 gains only 1–1.5% and takes half as long again): Go 1.27's level 6 finds few repeated sequences, whereas level 7 produces files about 5 times smaller for gradients and icons and 4–25% smaller for photographs.
- PNG data is compressed in 256KB blocks (as in pigz), allowing multiple cores to share the work. When the image data fits within a single block, the file is identical to that of previous versions. With Go 1.27 or later, data of more than one block is compressed up to level 7 by `klauspost/compress`'s flate, which writes the bytes Go 1.27's `compress/flate` writes and takes each block's dictionary when it is reset, where `compress/flate`'s has to be made anew for every block: a 24-megapixel PNG allocates 3MB instead of 276MB and peaks at 9.2MB instead of 16.6MB (15.0MB instead of 23.0MB with 4 threads), 6% faster, with the same bytes.
- Animated GIF output: a single palette is chosen for all frames (`GIFOptions.Colors` and `NoDither` now apply to animations), and frames after the first store only the changed rectangle. `GIFOptions{FixedPalette: true}` continues to write full frames with the fixed palette, frame by frame. The pixel limit is checked before any frame is processed. `NoDither` also applies with `FixedPalette`.
- Lossy WebP: segment-based quantization, following libwebp's spatial noise shaping.
- Lossy WebP: `WebPOptions.Effort` applies to lossy output too (it was for lossless only). The default, 5, converts colours with sharp YUV, quantizes 4×4 blocks by trellis and chooses the loop filter levels by measuring, as libwebp does at its best settings; chroma DC errors are diffused at every effort; quantizers and rate-distortion weights were tuned on SSIMULACRA2 and butteraugli. On 14 images: 6.6% / 9.5% smaller than libwebp's default and 1.3% / 2.2% smaller than its best settings (`-m 6 -af -sharp_yuv`), at equal SSIMULACRA2 / butteraugli. Encoding takes 2 to 2.6 times as long; `Effort: 1` keeps the earlier speed and is still 6.1% / 4.8% smaller than libwebp's default.
- Lossy WebP with transparency: the alpha plane is coded by the lossless encoder at its default effort, through the better of no filter and the horizontal one (all four filters from effort 7), with the optimal parse for planes of up to 4 megapixels (all from effort 7), and the colours of transparent areas are made cheap, as libwebp does: a photograph in a soft round window 50% smaller (146KB to 73KB at quality 75; libwebp 88KB), alpha chunks up to 6 times smaller (Tux's 2% smaller than libwebp's). Up to 8MB more memory while the plane is coded; under a low memory limit the alpha chunk (not the pixels) can differ, as lossless files can.
- Lossy WebP is decoded to the pixels libwebp, and so browsers, show, to the byte: chroma interpolated between samples and libwebp's integer conversion (before, each chroma sample covered its 2×2 block and the colours differed by about half a level on average, up to 20–40 at colour edges). Decoded lossy WebP is now RGB; `Metadata()` still reports it as `ycbcr`.
- Lossless WebP chooses its LZ77 matches by the cheapest path through the pixels (the idea of libwebp’s TraceBackwards), searches further for repeats in screenshots, and tries several block sizes and numbers of Huffman groups: 5.5% smaller over 17 images at the default effort (screenshots 6–9%), in 3.8 times the time (42s against 11s on one core; libwebp's default takes 24s); 5.3% smaller in total than libwebp’s slowest setting (5.7% at effort 9, in 106s against its 308s). At every pixel the longest match at the nearest distances above and to the left is offered besides the hash chain's (a gradient mask 16% smaller), and prefix codes are evened out for run-length coding of their lengths when that pays, as libwebp does. Images of up to 4 megapixels also race a variant with libwebp's cross-color transform (icons and interface pictures with colour gradients 2–9% smaller), their split into Huffman groups is also tried without the colour cache (an icon 4% smaller), and their variants without the predictor also try matches only at distance 1 and a row up, as libwebp's "RLE" references (icons of few colours 3–4% smaller). A 6000×4000 photograph from a JPEG, whose noise leaves the parse little to find, comes out the same size, in 5.1s instead of 4.1s and at most 25.6MB instead of 22.2MB.
- Lossless WebP selects each band's predictors using the cost model as it stands at the start of that band, so that they can be selected in parallel; output files differ slightly.
- The command-line code has moved from `cmd/goimgtools` to package `cli`; `cmd/goimgtools` builds the same program.

### Fixed

- `Extend` and `FitContain` of an image with transparency kept as NRGBA (a PNG with alpha) went through premultiplied 8-bit RGBA, which moved the colours of translucent pixels (by up to 255/alpha levels: 4 at alpha 55); they keep them now.
- `FastShrinkOnLoad` on a JPEG whose components are sampled in ways the decoder does not reduce itself (Go's test files 121121, 211211, 221122, 222112) failed with "shrink: unsupported pixel type"; the decoded image is averaged again.

- A compressed TIFF of a large image was one strip, which libvips (and so sharp) refuses once its compressed data exceeds 50MB: compressed images of more than 1MB of pixel data are now written in strips of about 1MB.
- On processors that fuse a multiplication and an addition into one instruction (ARM64, such as Apple silicon and AWS Graviton, POWER, s390x, RISC-V, LoongArch), some results could differ from those on x86 by a level or a pixel: `Linear`, the blend modes, `Convolve` with fractional weights, the palettes of GIF and few-colour PNG, the Mitchell kernel, watermarks placed by ratio, the size of `RotateBy`, `Blur`'s boxes, text outlines, and choices made by the lossless WebP and jpegli encoders. Every product is now rounded before it is added, as on x86, and CI checks that the compiler fuses none of them on those processors.
- A panic in an operation could leave the chain's input open, retaining memory budget and temporary files.
- `Frames().LoopCount` of a GIF was its repeat count, one less than the number of times it plays, which is what the field documents.

## 0.1.0 (2026-11-14)

Initial public release: reading and writing PNG, JPEG, WebP, GIF (including animation), BMP and TIFF a few rows at a time within a memory limit; resizing (six kernels, five fit modes), cropping, rotation by multiples of 90°, flipping, flattening, compositing and watermarks, text; JPEG with optimized coding tables and progressive encoding, PNG colour reduction, `MaxFileSize`; batch processing; extension interfaces (`Pipe`, `Pixels`, `Apply`, `FromImage`, `FromSource`, `RegisterFormat`, `Stream`, `ToImage`, package `pipeline`); the `info`, `check`, `compare` and `formats` commands, and package `inspect`; input and output pixel limits, cancellation, and panics returned as errors.
