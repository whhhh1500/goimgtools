# Compatibility and comparisons

## Compatibility with the standard library

Decoding and encoding of PNG, JPEG, GIF, BMP and TIFF, as well as the default resizing, are adapted from the code of the standard library and `x/image`. Only the parts that operate on the whole image were changed to operate row by row; the pixel arithmetic and its order are unchanged. The tests verify the following byte for byte:

- Decoding: the 164 test images shipped with Go and `x/image` (PNG 85, JPEG 31, TIFF 17, WebP 17, BMP 9, GIF 5) decode to the same pixels as with the standard decoders (for JPEG and WebP, see below); for truncated files and files with a single corrupted byte, this library reports an error wherever the standard decoder does.
- Resizing: the default algorithm is byte-for-byte identical to `draw.CatmullRom.Scale`. Grayscale images are computed on a single channel and output as grayscale; the values are those of the three equal red, green and blue channels produced by `x/image`.
- Encoding: GIF (with `FixedPalette`; with `NoDither` also set, identical to `gif.Encode` using `draw.Src`) is byte-for-byte identical to the standard library (JPEG is written as libjpeg-turbo writes it, see below); BMP and TIFF are byte-for-byte identical to `x/image` (without metadata or a resolution, and for compressed TIFF up to 1MB of pixel data: larger compressed images are written in strips of about 1MB, as libtiff writes them, where `x/image` writes one strip, which libvips cannot read once its compressed data exceeds 50MB). PNG (without colour reduction) is byte-for-byte identical to `png.Encode` when level 6 is used (specified, or the default with Go 1.26) and the image data does not exceed one compression block (256KB); with Go 1.27 the default is level 7 (see [Compression](compression.md)), and larger images are compressed in blocks, with identical pixels.
- Blur and unsharp mask: for images without an alpha channel, `Blur` is byte-for-byte identical to `GaussianBlur` in Pillow 12.1.1, and `Sharpen(SharpenOptions{...})` to its `UnsharpMask` (the tests include reference images generated by Pillow, sigma 0.7–40). The algorithms and the fixed-point arithmetic are ported from Pillow's C code. `Blur` with `BlurLibvips` is byte-for-byte identical to sharp 0.35's `blur` on 8-bit images, with and without transparency (checked at sigma 0.7, 2, 3 with `minAmplitude` 0.01, 25 and 300): the same integer weights and rounding as libvips' `gaussblur`, its 8-bit vector path and, for masks wider than 1024, its integer path, and its premultiplication in single precision.
- Box blur: `BoxBlur` is byte-for-byte identical to Pillow 12.1.1's `ImageFilter.BoxBlur` for images without an alpha channel, at whole and fractional radii (checked from 0.5 to 200, in colour and grey; the tests keep 14).
- Rotation as Pillow: `RotateBy` with `RotatePillow` is byte-for-byte identical to Pillow 12.1.1's `Image.rotate` (nearest in 16.16 fixed point, bilinear and bicubic in double precision with the fraction dropped, an image with transparency premultiplied for those two as Pillow's `RGBa`, the fill included; `expand`; half turns and quarter turns of square images as plain turns): checked on 168 rotations of colour, transparent and grey images, the tests keep 84. Pillow on processors whose compilers fuse a multiplication and an addition may differ.
- Transforms as Pillow: `Transform` is byte-for-byte identical to Pillow 12.1.1's `Image.transform` with `AFFINE`, `EXTENT`, `PERSPECTIVE` and `QUAD` (its extent and quad coefficients worked out as its Python does; nearest as `ImagingTransformAffine` and `ImagingGenericTransform` pick, the same filters as rotation): checked on 141 transforms of colour, transparent and grey images, including a perspective that divides by 0 along a line (whose points count as outside, as on x86), all kept in the tests. `MESH` is not offered. `TransformPerspectiveQuad` works out its perspective from the corners (Heckbert's mapping of a square to a quadrilateral): in the tests it gives the pixels of Pillow with the coefficients the Pillow cookbook's `find_coeffs` solves for with numpy.
- Grayscale: byte-for-byte identical to Pillow's `convert("L")`, i.e. the luma of `color.RGBToYCbCr`; across all 16.77 million colours, it deviates from the exact Rec. 601 luma by at most 0.5 levels. (`color.GrayModel` first computes a 16-bit value and then discards the low 8 bits; it deviates by up to 0.99 levels and does not yield the nearest level for 16% of colours, so it was not adopted.)
- Colour adjustment: differs from `modulate` in sharp 0.35 (libvips 8.18) by at most 1 per pixel, 0.14 on average.
- `Trim`: the box is sharp 0.35's `trim` box, size and offset, on the same pixels (checked on a noisy JPEG border at thresholds 0, 3, 10 and 40, specks of dust, line art with and without `LineArt`, a background given, and margins).
- **Resize as sharp**: with `ResizeOptions.Method` `ResizeLibvips`, `Resize` gives sharp's pixels, to the byte. It goes through libvips' resize step by step, in the same arithmetic: down the columns and then across, each direction rounded to 8 bits; the part of a reduction beyond 2 averaged in boxes in fixed point (`vips_shrinkv`, `vips_shrinkh`), the rest a window of the kernel placed at 1/64 of a pixel with weights in 12-bit fixed point (`vips_reducev`, `vips_reduceh`), each output's place worked out afresh at the start of each row and, down the columns, of each run of 10 rows (the tiles of the cache libvips puts after `vips_reducev` when sharp reads in order) and added to after; `KernelNearest` subsampling first; enlargement by `vips_affine`'s nearest, bilinear or bicubic interpolator with the edges repeated, or `vips_zoom`; colours multiplied by alpha in 8 bits before and divided after, as sharp does, and the background `FitContain` pads an image with transparency with multiplied and divided too (when the image is resized: otherwise sharp pads with the colour as it is); a JPEG shrunk on load by the factor sharp picks, with libjpeg's scaled decoding, cut to libvips' `floor(w/k)` × `floor(h/k)`; with `FastShrinkOnLoad` a WebP scaled on load to libvips' `rint(w/s)` × `rint(h/s)` as libwebp scales it (`use_scaling`: each plane averaged over the area of each pixel in 32-bit fixed point, the chroma of a lossy image from its own size, the loop filter skipped when both sides go below three quarters, a lossless image with its colours multiplied by alpha). Checked against sharp 0.35.5 (libvips 8.18) on 578 resizes (every kernel; reducing by 1.01 to 40, enlarging up to 3 times, both at once; sides of 1 pixel; with transparency and in grey; every fit and position, translucent backgrounds; turns before and the EXIF turn; JPEGs shrunk on load, 4:2:0, 4:2:2, progressive 4:4:4 and grey, by 2, 4 and 8; lossy, lossy with alpha and lossless WebPs, odd sizes, every fit and kernel); the tests keep 180 of them. The scaled decoding of WebP is also checked against libwebp's `dwebp -scale` on 14 files at 7 sizes each (simple and normal loop filter, kept and skipped). A 16-bit image is resized in 8 bits (sharp keeps 16).
- **Resize as Pillow**: with `ResizeOptions.Method` `ResizePillow`, `Resize` gives Pillow's `Image.resize`, to the byte: its weights (the filter at each source pixel's distance from the output pixel's centre, scaled when reducing, normalised, in 22-bit fixed point), its two passes (across, only the rows the second reads, then down, each rounded to 8 bits), its premultiplication of RGBA and LA (`RGBa`, `La`: c·a/255 rounded, divided back as whole numbers), and its nearest (an affine scaling whose places are added pixel after pixel). Checked against Pillow 12.1.1 on 346 resizes (every filter; reducing up to 30 times and enlarging up to 3; sides of 1 pixel; RGB, RGBA, L and LA; turned first; JPEGs after `draft`); the tests keep 57 of them. With `ReducingGap` it is Pillow's `Image.thumbnail` and `resize(…, reducing_gap=…)`: the size by the nearest aspect ratio, a JPEG drafted for the box times the gap and resized from the box draft gives, `Image.reduce` first (the box the filter reaches, each cell `((sum + n/2) · m) >> 24` with `m` = 2³²/(256n) in single precision); checked on 90 more (PNG in RGB, L and RGBA, baseline and progressive JPEG, every filter, gaps 1 to 5.5). Its fits are `ImageOps.contain`, `cover`, `pad` and `fit`, sizes and places rounded half to even as Python rounds, `fit` resizing its fractional crop box straight to the box: checked on 90 more; the tests keep 32.
- **Pillow's ImageOps and ImageEnhance**: `Posterize`, `Solarize`, `Equalize`, `AutoContrast` (cutoffs, ignored levels, `PreserveTone`) and `Enhance` (colour, contrast, brightness, sharpness) give Pillow 12.1.1's `ImageOps.posterize`, `solarize`, `equalize`, `autocontrast` and `ImageEnhance` results, to the byte: their tables worked out as Pillow's Python does (the cutoffs with Python's float floor division), `Image.blend` in single precision with the fraction dropped, the mean lightness of `ImageStat`, and the `SMOOTH` filter in single precision with the edge pixels kept. Checked on 638 cases (RGB, L, RGBA, noise; enhancement factors from −0.5 to 3.7); the tests keep 69. `Filter` (the ten built-in filters) and `Convolve` with `ConvolvePillow` (`ImageFilter.Kernel`) are Pillow's `im.filter`, to the byte, on 240 cases (RGB, L, RGBA, LA, images smaller than the kernel); the tests keep 36. Pillow's `ImageOps` refuses images with transparency; here they are worked out on red, green and blue, alpha kept.
- Cover crops: a centred crop is where sharp puts it (the odd pixel to the right and below). `InterestingEntropy` chooses the crop libvips' smartcrop chooses on the same pixels (checked on eight crops of four photographs); since this library resizes slightly differently from libvips by default, its pixels, and in close cases the crop, can differ from sharp's (6 of 8 the same); with `ResizeLibvips` the pixels are sharp's. `InterestingAttention` follows libvips' method, shrinking as libvips does; it chose sharp's crop in 6 of 6 checked cases (and libvips' on the same pixels in 5 of 6).
- `inspect.Stats`: `Channels`, `Entropy` and `Sharpness` are sharp 0.35's `stats()` `channels`, `entropy` and `sharpness` (the levels, their first positions and their sums exactly, the means, deviations, entropy and sharpness to 12 significant digits; checked on four images, with and without transparency, and greyscale). sharp's `dominant` is the middle of the fullest of 4096 bins; `Dominant` lists up to five colours, each the mean of what it covers.
- Levels and filters after sharp 0.35: `Negate` (with and without `Alpha`), `Linear`, `Threshold` (images without transparency; `PerChannel` too), `Median`, `Convolve` and `Grayscale` with `Linear` are byte-for-byte identical to sharp's `negate`, `linear`, `threshold` (`greyscale: false` too), `median`, `convolve` and `greyscale`; `Modulate` with `Lightness` is within 1 level of `modulate` with `lightness`; `CLAHE` is byte-for-byte identical to `clahe` (libvips' `hist_local`; a window larger than the image, which libvips refuses, is mirrored again); `Normalize` is within 1 level of `normalise` (the percentiles of lightness are libvips' `vips_percent` exactly: whole levels, counts scaled and truncated as `vips_hist_norm` does, and the first level above the percentage); `Tint` is within 1 level of `tint` (its grey is libvips' `B_W` exactly). `Median` is also byte-for-byte identical to Pillow's `MedianFilter`, alpha included. The blend modes of `Composite` are within 1 level of sharp's `blend` on an opaque image (libvips applies the PDF blend formulas to colours multiplied by alpha, not as they are, and this library does the same, so that the results agree); over a transparent image the visible (alpha-weighted) colours are within 3 levels. `Gamma` follows ImageMagick's `-gamma` (sharp's `gamma` applies only around resizing). Unlike sharp, `Threshold` keeps transparency rather than thresholding it. `RotateBy` is byte-for-byte identical to sharp's `rotate` (30, 60, −17.5 and 200 degrees, and 45 with transparency): an `Affine` by the turn's matrix, its sine and cosine rounded correctly as libvips' C library gives them (Go's `math.Sincos` can be a unit in the last place off, which at 30 degrees moves the box by a pixel). `Sharpen` with `SharpenLibvips` is within a level of sharp's `sharpen` with a sigma, on 1 to 3 values of 46350 (and to the byte with transparency, and at sigma 0.6): it goes through libvips' LabS step by step in the same precision (its table of linear light, XYZ in single precision, its interpolated table of cube roots, LabS with the fraction dropped, the integer Gaussian of the lightness, its table of 65536 entries for the curve, and back), and the levels that differ come from libvips' cube roots, which it takes from the C library's `cbrtf`: on Windows 31% of them are a unit in the last place off the exact ones, which this library uses, and other systems differ again. `Affine` is byte-for-byte identical to sharp's `affine` with its default bilinear interpolation, and with its nearest and bicubic interpolators (a turn, an enlargement, offsets with a background; with and without transparency): the same output box, the same stepping of the source point (afresh at each of libvips' tiles of 128 columns), its 12-bit fixed-point weights and, with transparency, its single-precision premultiplication. `Dilate` and `Erode` are byte-for-byte identical to sharp's `dilate` and `erode` (on a photo, after `threshold`, with transparency, and wider than the image); `Rank` to Pillow's `RankFilter`, `MinFilter` and `MaxFilter`. `Recomb` (3×3 and 4×4) and `Unflatten` (with and without transparency, and after `Threshold`) are byte-for-byte identical to sharp's `recomb` and `unflatten`; `ExtractChannel` and `RemoveAlpha` give the stored levels, as sharp's `extractChannel` and `removeAlpha` do.
- Conversion to sRGB: for three profiles, Display P3 (encoded both as a sampled curve and as a parametric curve) and Adobe RGB (gamma curve), every value differs from LittleCMS by at most 1, and about 1.6% of values differ by 1. Profiles of lookup tables (lut8, lut16 and lutAToB, to Lab or XYZ, RGB and CMYK) are converted by their perceptual table, interpolated as LittleCMS interpolates (tetrahedrally; in four dimensions, between two tetrahedral interpolations along the first), on a grid of 17 points each way for CMYK and 33 for RGB, as LittleCMS optimizes an 8-bit transform: a CMYK printing profile (Windows' RSWOP, lut16 to Lab) gives LittleCMS's perceptual conversion to within 1 level on 15,900 colours (0.7% differ), and the test profiles of each kind within 1 (CMYK) and 3 (RGB). The black point is compensated as LittleCMS (2.17, and 2.20) compensates it in a perceptual conversion to a version 4 sRGB profile, which Pillow's `ImageCms.createProfile("sRGB")` and sharp's sRGB profile are: the black of the profile (fixed for a version 4 perceptual table; for version 2, the neutral grey as light as the most ink, or RGB 0, gives) is taken to sRGB's black, linearly in XYZ, the white kept. A CMYK file without a profile, or with one that cannot be read, is converted through libvips's CMYK profile (Graeme W. Gill's "Chemical proof", in the public domain), as libvips and sharp convert it: within 1 level of LittleCMS 2.17 on 16,384 colours (0.9% differ). sharp 0.35.5's results differ from these by up to 24 levels in dark colours, because the LittleCMS it is built with (2.19) does not make the black point neutral, which 2.20 restores: with the black point kept as it is, the same conversion gives sharp's within 1 level. An image made in memory (`FromImage`) as `*image.CMYK` without a profile keeps the values `color.CMYK` gives. A grey profile (a tone curve, as Photoshop's dot gain profiles) maps each grey to sRGB's grey of the same luminance, the image staying grey: the same as LittleCMS for the test profile.
- Rotation by any angle: at 2 pixels or more from the edges, every pixel differs from Pillow's bilinear rotation (`expand=True`) by at most 1. The edges differ by design: this library blends the outermost ring of pixels with the background according to coverage (as libvips does), producing a smooth edge, whereas Pillow produces a hard edge. The canvas is the smallest size that contains the whole image, and the three implementations each compute it differently: rotating 150×103 by 30° gives 182×165 in this library and Pillow, whereas sharp rounds to 181×164 (cutting off a small part of the corners).
- The output of all new operations and of each encoder is byte-for-byte identical on x86-64 and 32-bit x86; ARM64, PowerPC, s390x, RISC-V, LoongArch and MIPS are verified by the checksum tests in CI (in floating-point arithmetic, each product is rounded before it is added, so that processors that fuse a multiply and an add into a single instruction do not produce different results; CI compiles the library for ARM64, POWER, s390x, RISC-V and LoongArch and fails if the compiler fuses any).

## Intentional differences

- **GIF palette**: the standard library reduces every non-paletted image to a fixed set of 256 colours (the Plan 9 palette), which yields only 25dB on photographs. By default, this library selects colours based on the image content, reaching 39dB on the same photograph; a UI screenshot improves from 29dB to 58dB, with a smaller file as well. `FixedPalette` restores the standard library's behaviour. For animations, colours are likewise selected from all frames together. Against sharp 0.35 (libvips writing GIF through cgif with libimagequant, at its default effort 7), on 19 photographs fitted into 1024×1024: SSIMULACRA2 64.3 against 63.9 and butteraugli (3-norm) 2.24 against 2.45, for files 0.5% larger; on two UI screenshots, 93.7 and 92.4 against 92.6 and 92.2, the files the same size. The 6000×4000 photograph fitted into 1536 and written as GIF takes 0.42s on one core, sharp 1.92s (0.38s at its fastest effort, 1, whose file is 11% larger).
- **JPEG files**: a JPEG is written as libjpeg-turbo writes it by default, and so Pillow and sharp, to the byte: libjpeg's colour conversion, its 4:2:0 and 4:2:2 downsampling (the rounding bias alternating across, the chroma below the image repeating its last row), its accurate integer forward DCT, its rounding in quantizing, its dummy blocks past the right and bottom edges, its optimized Huffman tables (`Optimize`) and its markers (a DQT and a DHT segment for each table). Pillow's file has a JFIF segment besides, which this library writes only with a resolution; sharp writes none (it drops metadata by default), and its files are identical as they are. Checked on 310 files Pillow 12.1.1 wrote (1×1 to 1200×900, qualities 1 to 100, 4:2:0, 4:2:2, 4:4:4, grey, optimized tables) and 96 sharp 0.35.5 wrote; sharp writes a grey image with three components (it converts it to sRGB first), this library with one, as Pillow does. Progressive files use scans of mozjpeg's choosing, not libjpeg's simple progression. The standard library's encoder, which this one followed before, differs in its colour conversion, its DCT and its downsampling, by a level or so.
- **JPEG pixels**: JPEG files are decoded as libjpeg-turbo decodes them by default, and so Pillow and sharp, to the byte: its accurate integer inverse DCT, its "fancy" triangle filter that brings subsampled chroma back to full size (across, down or both, with the held-back row at the edge of each band of rows), and its YCbCr to RGB tables (checked on 57 files Pillow wrote, from 1×1 to 401×233, every subsampling, baseline and progressive, restart markers; on 2001×1501 files that span many bands; and on Go's JPEG test files). The standard library uses another inverse DCT, repeats each chroma sample instead of interpolating, and converts with other rounding: on a 4:2:2 photograph its pixels are up to 23 levels from libjpeg-turbo's (PSNR 39.9 dB) and 0.36 dB further from the original. Not converted as libjpeg does: components sampled in ways no encoder chooses (Go's test files 121121, 211211, 221122 and 222112, whose components are repeated to full size), CMYK and YCCK files, and `FastShrinkOnLoad`, which reduces the blocks of every component alike with libjpeg's reduced inverse DCTs (libjpeg reduces the chroma of a 4:2:0 file by half as much). Shrunk on load for `ResizeLibvips`, a JPEG is decoded as libjpeg-turbo's scaled decoding does it, to the byte, which is Pillow's `draft` too (checked on baseline 4:2:0 and 4:2:2, progressive 4:4:4 and grey files, by 2, 4 and 8). A JPEG that goes straight into a JPEG or lossy WebP file, with no operation between, keeps its YCbCr as stored: its chroma is not brought to full size and reduced again.
- **Lossy WebP colours**: `x/image` converts WebP luma and chroma as if they used JPEG value ranges, so colours have lower contrast than with libwebp (as in browsers), 6–8 levels on average and 33 at most, and it takes each chroma sample for its whole 2×2 block, which leaves blocks of colour along edges. This library converts as libwebp does (chroma interpolated between samples, libwebp's integer arithmetic): the decoded pixels are libwebp's (`dwebp`) to the byte, checked on the lossy files of `x/image`, files with odd sizes and alpha, and a 15.5MP photograph. `Metadata()` still reports such files as `ycbcr`, which is how they are stored.
- **TIFF with JPEG compression**: TIFF files whose strips or tiles are JPEG streams (compression 7, as libtiff writes them, and libvips and sharp by default), which `x/image` rejects, are read: each block decoded as a JPEG with the tables the blocks share (JPEGTables), in colour (YCbCr) and grey. The pixels are those the same JPEG streams give as files (checked on files built from strips with and without shared tables, and on sharp's TIFFs in strips and in tiles).
- **Resolution**: a resolution the input records is written to JPEG, PNG, TIFF and BMP output by default (a JFIF segment, a pHYs chunk, the resolution tags, the header fields), which the standard library does not write; JPEG output from an input without one is unchanged (no JFIF segment), and so is every output after `Density(0)`. The resolution is read as sharp 0.35 reads it (checked on JPEG, PNG, TIFF and WebP files sharp wrote, and sharp reads back what this library writes): the EXIF block's first, 25.4 pixels per inch or less taken for none; pixels per metre or centimetre that a whole number of pixels per inch is stored as give that number, where sharp rounds every resolution to a whole number.
- **ICC**: if the input has an ICC profile, it is written to the output by default, so for such images the output contains ICC data that standard library encoding does not; after `StripICC()`, the outputs are identical.
- PNG output from JPEG, YCbCr, CMYK and similar sources is written as 8-bit RGB, whereas `png.Encode` writes 16-bit.
- Baseline JPEG files in which a further scan follows a complete scan (very rare) are rejected.
- GIF, BMP and WebP images with a size of 0 are rejected; the standard library returns an empty image.
- Animated WebP files, which `x/image` rejects, give their first frame as the canvas shows it: the frame at its place, the rest of the canvas transparent; the frame's pixels are those of the same bitstream decoded as a still image.
- A JPEG quality outside 1–100 returns an error, whereas the standard library silently clamps it to the valid range.
- A progressive JPEG read from a stream (`FromReader`) has its coefficients stored in 16 bits; an out-of-range value (which occurs only in corrupt files) returns an error. An end-of-band run that a corrupt progressive scan leaves unfinished ends with that scan, as in libjpeg, which the decoding of the scans in step needs; the standard library carries it into the next scan.
- **Blur and sharpening of images with an alpha channel**: computed with premultiplied alpha, so the colour of transparent pixels does not bleed into neighbouring pixels; Pillow blurs each of the four RGBA channels separately, and the colour of transparent areas (often black) darkens the edges.

## WebP encoders

The WebP encoders were written for this module. As there is no standard library implementation to compare against, they are verified with two decoders: `x/image` and libwebp (via Python PIL) decode the output to the same result, and lossless encoding is restored pixel for pixel. Comparison with libwebp (test environment as in [Benchmarks](performance.md#benchmarks)):

- Lossy: 14 images (photographs, game artwork and a wallpaper gradient, 0.06 to 15.5 megapixels), each encoded at qualities 45–95 and decoded with libwebp, compared with libwebp 1.6 (`cwebp`) by file size at equal SSIMULACRA2 and at equal butteraugli (3-norm; the 11 images up to 6 megapixels):

  | This encoder | libwebp default (method 4) | libwebp method 6 | libwebp best (method 6, `-af -sharp_yuv`) |
  |---|---|---|---|
  | Effort 5 (default) | 6.6% / 9.5% smaller | 4.6% / 7.0% smaller | 1.3% / 2.2% smaller |
  | Effort 3 | 7.1% / 8.5% smaller | 4.9% / 5.8% smaller | 1.0% / 0.9% smaller |
  | Effort 2 | 6.1% / 4.8% smaller | 3.6% / 1.4% smaller | 0.2% / 2.4% larger |
  | Effort 1 | 4.0% / 1.2% smaller | 1.5% smaller / 2.2% larger | 2.2% / 5.4% larger |

  On 11 interface pictures, screenshots and icons (converted to RGB), effort 5 is as small as libwebp's best at the same SSIMULACRA2 (27.4% smaller than libwebp's default, libwebp's best 27.2%; per image from 4% larger to 11% smaller).

  At the same quality setting, files are about 2.5% smaller than those of libwebp's default and score higher. Time for a 3840×2160 photograph (from PNG) on one thread: 0.43s at effort 1, 0.54s at effort 2, 0.79s at effort 3, 0.99s at effort 5 (8 threads: 0.32s); `cwebp` takes 0.53s at its default, 0.81s at method 6 and 3.03s at its best settings.
  - Segment-based quantization is ported from libwebp (macroblocks are divided into 4 segments according to the distribution of their coefficients, with finer quantization in flat areas and coarser quantization in textured areas, at libwebp's default strength).
  - From effort 3, colours are converted with libwebp's sharp YUV: rather than averaging the colour of each 2×2 block, it looks for the luma and chroma from which a decoder's chroma interpolation gives back the source most closely. On thin saturated lines the luminance of the decoded image comes 3–9 dB closer to the source's; decoders that interpolate chroma (libwebp, so browsers, and this module's) show the difference, those that do not (`x/image`) do worse with it. From effort 3 too, 4×4 blocks are quantized by trellis, as libwebp does (libwebp also does it for 16×16 blocks, which made files about 1% larger here).
  - From effort 5, the loop filter level of each segment is chosen by filtering the reconstruction at levels around the starting one and measuring it by SSIM, as libwebp's `-af` does.
  - At every effort, the rounding error of the DC of each chroma block is carried over to the blocks to its right and below (libwebp's error diffusion), which breaks up the bands of smooth colour gradients.
  - The quantizers of luma and chroma, the rate-distortion weights and the loop filter strength were tuned on these measurements (SSIMULACRA2 and butteraugli), on 9 of the images, and checked on all 14. libwebp's other psychovisual terms (a texture distortion term, raising high frequencies before quantization, penalties for flat blocks) were tried and made no difference.
- Transparency in lossy files: the alpha plane is coded as libwebp codes it, by the lossless encoder (colour table, LZ77, colour cache) at its default effort, through no filter or the horizontal filter (all four filters from effort 7), whichever its fast parse makes smaller, and then with its optimal parse (for planes of up to 4 megapixels; larger ones from effort 7, as the parse takes several seconds there); it used to be coded with runs and copies from the row above only. The colours of transparent pixels, which cannot be seen, are made cheap as libwebp makes them unless asked not to (`-exact`): wholly transparent 8×8 blocks flat, and in partly transparent blocks the luma of the transparent pixels evened out. Alpha chunk, against libwebp 1.6 at its default and with `-m 6 -alpha_filter best`: a photograph in a soft round window 8.4KB (22.4KB, 7.4KB), an icon 1.33KB (1.33KB, 1.33KB), Tux 3.40KB (3.46KB, 3.43KB), a drawing 3.42KB (3.56KB, 3.43KB); with the earlier coder, 51.8KB, 1.91KB, 4.98KB and 3.61KB. The photograph at quality 75: 146KB with the earlier coder, 73KB now, 88KB with libwebp. While it codes the plane, the lossless encoder takes up to 8MB more memory.
- Lossless: at the default level, on 17 screenshots, photographs and game artwork, 5.3% smaller in total than libwebp 1.6 at its slowest setting (method 6, quality 100) and 5.6% smaller than at its default (method 4), in 42s against 308s and 24s; per image from 3.2% larger (a screenshot) to 9.8% smaller (photographs). At effort 9 (106s), 5.7% smaller than libwebp's slowest setting, and within 1.1% of it on every image (a screenshot). Screenshots are where libwebp's slowest setting still leads at the default level (by up to 3.2%): its LZ77 window covers the whole of a screenshot, the default level's half of it at most, to keep memory down. Effort 7, which looks twice as far back, makes two screenshots 1.3% and 2.1% smaller, for 4 to 15MB more memory at its peak. On 30 icons and interface pictures of Windows (2KB to 36KB as WebP), 4.3% smaller than libwebp's default and as small as its slowest setting (0.08% larger, less than the colour profile one of them keeps and libwebp drops). For images of up to 4 megapixels three things are tried besides: a variant with libwebp's cross-color transform runs against the others, without subtract green, which makes those with colour gradients 2–9% smaller (it has to be ahead by 3% while the variants race, and by 1% at the end, as what was coded so far misjudges it); and the split into Huffman groups is made without the colour cache too, as the cache, chosen for one group, can cost more than it saves once the image is split (an icon 4% smaller); and the variants without the predictor also code their pixels with matches only at distance 1 and a row up, taken greedily (libwebp's "RLE" references), kept when 2% smaller: on pictures of few colours the cheap codes of those two distances beat the best matches found anywhere (three icons 3–4% smaller). None of them helps photographs; on larger images they would add 2–4MB to the peak of memory and, for the second, 40% to the time. The LZ77 matches are chosen by the cheapest path through the pixels (the idea of libwebp's TraceBackwards), which searches for a match at every pixel; where the matches at each distance end is remembered, so that the long repeats of screenshots are not compared again and again (the same files in a third of the time), and in flat areas the search passes over the pixels of the run it is in, which match no better than the pixel before, while the parse no longer goes through every pixel of a long match from every pixel (drawings and alpha planes in a third of the time or less). Besides the match the hash chain finds, the longest one at the nearest distances above and to the left (those with the cheapest codes, which libwebp's LZ77 "box" searches) is offered at every pixel: the hash chain, which goes through the latest pixels first, rarely gets as far as the rows above in smooth areas, where the residuals repeat those a few rows up (a gradient mask 16% smaller, Tux's alpha plane 2%, photographs and game artwork up to 1%, in 15% more time). The prefix codes are made from counts evened out for run-length coding, and a code's zero lengths at the end are left out, when that makes the code with its lengths smaller (both as libwebp does). The blocks of the Huffman groups are chosen by trying several sizes. With little memory left the encoder tries fewer transform variants, so under a low memory limit the file can be larger (one 400×300 image: 2962 bytes at 6MB against 1972 bytes at the default 64MB); the pixels are the same. It is the one encoder whose bytes depend on the memory limit (and, through it, the alpha chunk of a lossy file with transparency).
