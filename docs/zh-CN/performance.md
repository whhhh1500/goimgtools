# 性能与基准测试

## 内存控制机制

- 各环节每次仅处理若干行（一个条带约 256KB），处理完成后传递给下一环节。
- 缩放不保留中间缓冲：每读入一行源图像，先完成横向缩放，再按权重直接累加到其影响的若干目标行。
- 须读取全图后才能输出第一行的情形，数据写入暂存区；已知内存容纳不下时直接写入磁盘。包括：隔行 PNG / GIF、从流（`FromReader`）读取的渐进式 JPEG、旋转与上下翻转、BMP 输出（文件须从最后一行开始写）、写文件头前须获知全图信息的编码（PNG 的透明度判断、WebP、压缩的 TIFF；此类情形暂存的是已压缩或已编码的数据）。
- 暂存数据至多占用内存上限的 1/8，其余写入磁盘。写盘开销很小（在 1200–2400 万像素图像上实测：隔行 GIF 耗时不变，渐进式 JPEG 慢约 20%，旋转耗时增加约 0.1 秒），而全部驻留内存会使中等尺寸图像的峰值内存达到 20–45MB。若需以内存换取速度，可调高 `MemoryLimit`：暂存数据小于上限的 1/8 时不访问磁盘。
- 所有随图像尺寸增长的缓冲均计入内存上限。上限不足时返回 `ErrMemoryLimit`，不会静默超额使用内存。
- `Rotate` 之后紧接 `Resize` 时，先缩小再旋转，暂存的是缩小后的图像。
- 从文件或内存读取的渐进式 JPEG（以及颜色分量分在不同扫描中的 JPEG）按扫描同步解码：先过一遍找出每个扫描的数据起点，再逐行块地让每个扫描依次解码该行（各自从文件中自己的位置读取），随即生成像素。只保留这一行块的系数（宽 6000 像素时 0.6MB），不再保存整幅图的系数（6000×4000 时 72MB，默认上限下写入临时文件）。细化扫描只访问非零系数。从无法重读的流读取时仍保存系数。

## CPU 与线程

默认单线程，CPU 占用始终不超过一个核心。`Threads(n)` 设置线程上限（最多为 CPU 核数）：

- `Threads(2)`：解码占用一个线程，缩放、合成与编码占用另一个线程。
- `Threads(3)`：编码另占一个独立线程（仅在不缩小且输出很大的转码中有收益）。
- `Threads(4)` 及以上：多出的核心分配给可分摊工作的环节——缩放、模糊、两种锐化、色彩调整、任意角度旋转、JPEG 编码（色彩转换、DCT、量化；熵编码仍为顺序执行）、PNG 压缩（按 256KB 分块压缩，见下文）、有损 WebP 编码（宏块分析、宏块行按波前推进、2/4/8 个系数分区分别重编码）、无损 WebP 的预测器选择与残差（LZ77 与第二遍仍为顺序执行）。这些环节将每批行、列或块分配给空闲核心共同计算。同一处理链中存在多个此类环节时也不会超出上限：多出的核心构成整条处理链共用的单一线程池，仅在空闲时借用，计算完成后即归还。
- 任一时刻处于工作状态的线程数不超过设定值；输出与单线程逐字节一致（测试对每种操作比较了 0、1、3、7 个辅助线程下的结果）。

线程之间通过固定 3 个条带的缓冲交接数据，消费方处理不及时，生产方即暂停等待；分摊工作的操作每批额外缓冲若干行。因此每增加一个线程约多占用 1–2MB 内存，并计入内存上限。暂存的行已写入临时文件时（内存上限很小），模糊与锐化退回逐行计算，不分摊工作。

实测数据（6000×4000，各线程数下结果逐字节一致）：

| 场景 | 1 线程 | 3 线程 | 4 线程 | 8 线程 |
|---|---|---|---|---|
| JPEG 转 JPEG，不缩小 | 0.61s | 0.43s | 0.33s | 0.27s |
| JPEG 转 PNG，不缩小（7 级） | 2.10s | 1.89s | 1.16s | 0.49s |
| RGB PNG 转 PNG，不缩小（7 级） | 1.58s | 1.01s | 0.71s | 0.45s |
| JPEG 缩小至 1536 | 0.41s | 0.23s | 0.22s | 0.22s |
| JPEG 转有损 WebP，不缩小 | 8.81s | — | 4.57s | 1.85s |
| 真实照片 3840×2160 转有损 WebP | 1.51s | — | 0.80s | 0.34s |
| 1080p 放大至 4K | 0.24s | 0.13s | 0.13s | 0.11s |
| 1080p 放大至 8K | 0.84s | 0.44s | 0.36s | 0.29s |

**PNG 分块压缩**：与 pigz 相同，过滤后的数据按 256KB 分块，每块以其前 32KB 数据为字典独立压缩，块尾执行同步刷新，各块首尾相接构成一条 zlib 流。分块方式与线程数无关，因此输出文件也与线程数无关；无辅助线程时，数据随到随压、直接写出，不额外占用内存。数据不超过一块（约 9 万像素的 RGB）时，输出与 `compress/zlib` 逐字节一致；更大的图像因每块重新开始查找重复数据，文件略大（2400 万像素实测 +0.005%）。

## JPEG 解码时缩小（可选）

`ResizeOptions{FastShrinkOnLoad: true}`（命令行 `-fast-shrink`）：JPEG 需缩小至原尺寸一半以下、且 `Resize` 为第一个操作（之前仅有旋转 / 翻转亦可）时，直接解码为原尺寸的 1/2、1/4 或 1/8，再完成其余缩放。每个 8×8 系数块解为 4×4、2×2 或 1×1 个像素，即由系数算出的块内像素平均值，与 libjpeg 的缩小解码相同，逆 DCT 的大部分运算因而省去。缩小 8 倍时每块即其像素的平均值，也就是 DC 系数除以 8，因此渐进式 JPEG 只解码 DC 系数的扫描。CMYK、RGB 的 JPEG 以及少见的子采样则完整解码后再做块平均。输出尺寸与不启用时相同，像素略有差异（平滑图像上平均不足 2 个色阶，黑白附近被截断的振铃处相差几个色阶），因此默认关闭。单核下，6000×4000 的基线 JPEG 缩到 400×400 以内用时 86ms（libvips 的 `vipsthumbnail` 同为单核：99ms），缩到 1536×1536 以内 185ms（152ms）；渐进式的分别为 50ms（230ms）与 322ms（279ms）。2 线程时缩到 1536 的两种情形为 111ms 与 247ms（`vipsthumbnail` 用其默认线程：171ms 与 300ms）。

## 实测

测试环境：Windows 10，Go 1.27.1。「标准库方案」指以 `image.Decode` 整图解码、以 `x/image` 的 `CatmullRom.Scale` 缩放、以标准库编码。峰值内存为操作系统记录的进程物理内存峰值，其中约 5.4MB 为 Go 程序启动时的基础占用。

- 总 CPU 时间不随线程数变化（2 线程仅将相同的工作分配到两个核心上）。
- 渐进式 JPEG 按扫描同步解码（见[内存控制](#内存控制)）；此前其系数（6000×4000 时为 72MB）写入临时文件，6000×4000 一行耗时 0.87s、峰值 8.8MB。峰值多出的 1.6–1.8MB 中，0.6MB 是那一行块的系数，其余是堆变大后触发的一次垃圾回收，核心越多它触及的内存越多（`GOMAXPROCS=1` 时总共只多 0.5MB）。
- 启用 `FastShrinkOnLoad`（单线程）时：JPEG 基线 4:2:0 0.16s，4:4:4 0.25s，渐进式 0.30s。

- 旋转 90° 且不缩小时，96MB 像素数据存放于临时文件；全部驻留内存（上限 768MB 以上）时约 0.8s，峰值约 108MB。
- PNG RGB 6000×4000（41.6MB，与上表为同一图像）转无损 WebP：输出 27.6MB，峰值 25.8MB，5.35s（8 线程 4.67s）。（大图使编码器要求的各种分组块大小都变成同一种，原先对每种都把同一分组重做一遍：32.6MB、8.87s。0.1.0 版没有最优解析：22.2MB、4.15s，文件只大 0.004%：由 JPEG 解码而来的照片满是噪点，最优解析找不到多少可省的。）
- 带透明的有损 WebP（6000×4000 置于柔和圆形窗口中的照片，质量 75）：2.85MB，峰值 26.6MB，12.9s（8 线程 6.0s；透明通道改由无损编码器编码之前为 4.29MB、20.9MB、10.9s、3.1s）。透明通道在单核上编码，自用内存不超过 8MB；2400 万像素的平面在力度 7 以下不用无损编码器的最优解析。
- 有损 WebP 须先将全图转换为 YUV 并存储，逐一度量每个宏块后才能编码（分段量化所需，见[一致性与对比](compatibility.md#webp-编码器)）：转换后不超过 256KB 的小图驻留内存，更大的图像直接写入临时文件，仅逐行读回。实测对耗时无影响。
- 不缩小输出 GIF 耗时 2.0s（峰值 11.8MB）。使用固定调色板（`FixedPalette`）时为 4.3s：该路径的颜色查找顺序经过优化，结果与标准库逐字节一致，速度为逐个比较颜色的 3 倍以上。

### 画面调整操作（JPEG 基线 4:2:0 6000×4000，不缩小，输出 JPEG）

本库的耗时包含解码与编码。Pillow 一栏为同一台机器上 Pillow 12.1.1 仅执行该步骤的耗时（图像已解码于内存，单线程），用于比较算法本身的速度。

| 操作 | 1 线程 | 3 线程 | 6 线程 | 峰值内存（1 / 6 线程） | Pillow 仅执行该步骤 |
|---|---|---|---|---|---|
| 无操作 | 0.55s | 0.45s | 0.29s | 6.9 / 12.7MB | — |
| `Grayscale()` | 0.41s | 0.31s | 0.23s | 6.9 / 12.6MB | 0.02s |
| `Modulate(1.1, 1.3, 20)` | 1.08s | 0.56s | 0.54s | 7.3 / 14.2MB | — |
| `Blur(2)` | 0.98s | 0.56s | 0.30s | 10.2 / 17.9MB | 0.38s |
| `Blur(40)` | 0.88s | 0.57s | 0.25s | 16.4 / 24.4MB | 0.38s |
| `Sharpen()`（轻度） | 0.82s | 0.48s | 0.35s | 8.3 / 16.1MB | 0.24s（Pillow 的 `SHARPEN`，同为 3×3） |
| `Sharpen(SharpenOptions{Sigma: 2})` | 1.18s | 0.60s | 0.36s | 10.9 / 19.9MB | 0.48s |
| `Trim(10)` | 0.67s | 0.57s | 0.40s | 7.6 / 13.3MB | — |
| `Extend(50, 50, 50, 50, white)` | 0.64s | 0.49s | 0.30s | 7.9 / 15.4MB | 0.02s |
| `RotateBy(30, white)`，输出 7197×6465 | 1.25s | 0.73s | 0.68s | 12.6 / 19.7MB | 0.57s |

- 单线程（扣除无操作时的 0.55s）：模糊增加 0.43s，与 Pillow 的 0.38s 处于同一量级；旋转 30° 增加 0.70s，其中约 0.3s 用于编码多出的 2200 万像素（按每百万像素的编码耗时推算），旋转本身快于 Pillow 的 0.57s。
- 6 线程时，旋转的耗时停留在约 0.7s：其输出大一倍，编码相应更久。
- 内存上限降至 16MB（暂存的行写入临时文件）时，模糊、锐化、旋转与去边的结果与不限内存时逐像素一致（以 PNG 输出比对），耗时增加 0–15%，峰值内存均在 13MB 以内。

已评估但未实施的方案：

- 直接在 YCbCr 三个平面上缩放（色度平面仅为四分之一大小，缩放部分可提速近一倍）。其结果将不再与 `x/image` 逐字节一致，只能纳入 `FastShrinkOnLoad` 这类「像素略有差异」的可选项；该模式下缩放仅占总耗时的约六分之一，预计整体提速约 9%，而改动面较大。
- PNG 压缩改用 `klauspost/compress`：Go 1.27 标准库的压缩已属同类快速实现，替换后无收益。

复测方法：

```bash
go build -o memprobe.exe ./cmd/memprobe
```

```bash
./memprobe.exe api in.png out.jpg 1536 1536 logo.png
```

```bash
./memprobe.exe std in.png out.jpg 1536 1536 logo.png
```

环境变量：`GOIMG_MEM`（内存上限，MB）、`GOIMG_ADJUST=gray|modulate|blur:SIGMA|sharpen|usm:SIGMA|trim|extend|rotate:度数`（缩放后追加一项调整）、`GOIMG_THREADS`（线程数，可超过 3）、`GOIMG_FAST=1`、`GOIMG_NORESIZE=1`（不缩小）、`GOIMG_ROTATE=1`（先旋转 90°）、`GOIMG_LOSSLESS=1`、`GOIMG_JPEG=opt|prog`、`GOIMG_COLORS=N`（PNG 减色）、`GOIMG_MAXSIZE=KB`、`GOIMG_ENLARGE=1`、`GOIMG_TEXT=文字`（平铺文字水印）、`GOIMG_PROF=文件名`（CPU 剖析）、`GOIMG_HEAP=文件名`（内存分配剖析）。
