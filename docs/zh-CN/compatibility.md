# 一致性与对比

## 与标准库的一致性

PNG、JPEG、GIF、BMP、TIFF 的解码与编码以及默认缩放均改写自标准库与 `x/image` 的代码，仅将处理全图的部分改为按行处理，像素运算及其顺序保持不变。测试逐字节比对以下内容：

- 解码：Go 与 `x/image` 自带的 164 幅测试图像（PNG 85、JPEG 31、TIFF 17、WebP 17、BMP 9、GIF 5）解码所得像素与标准解码器相同（JPEG 与 WebP 见下文）；对于截断文件和单字节损坏的文件，凡标准解码器报错者，本库同样报错。
- 缩放：默认算法与 `draw.CatmullRom.Scale` 逐字节一致。灰度图像仅计算单一通道并输出为灰度图像，其数值即 `x/image` 输出的红、绿、蓝三个相等通道的值。
- 编码：GIF（启用 `FixedPalette` 时；同时启用 `NoDither` 时与使用 `draw.Src` 的 `gif.Encode` 一致）与标准库逐字节一致（JPEG 按 libjpeg-turbo 的方式写出，见下文）；BMP、TIFF 与 `x/image` 逐字节一致（不含元数据和分辨率时；压缩的 TIFF 限像素数据不超过 1MB：更大的压缩图像按约 1MB 一条分条带写入，与 libtiff 相同，而 `x/image` 只写一条，其压缩数据超过 50MB 时 libvips 无法读取）。PNG（不减色时）在使用 6 级（指定，或 Go 1.26 下的默认值）且图像数据不超过一个压缩块（256KB）时与 `png.Encode` 逐字节一致；Go 1.27 下默认使用 7 级（见[压缩](compression.md)），更大的图像分块压缩，像素相同。
- 模糊与反锐化掩模：对于不含透明通道的图像，`Blur` 与 Pillow 12.1.1 的 `GaussianBlur`、`Sharpen(SharpenOptions{...})` 与其 `UnsharpMask` 逐字节一致（测试中存有 Pillow 生成的参考图像，sigma 0.7–40）。算法与定点运算移植自 Pillow 的 C 代码。使用 `MethodLibvips` 的 `Blur` 与 sharp 0.35 的 `blur` 在 8 位图像上逐字节一致，含透明与不含透明的图像均如此（核对了 sigma 0.7、2、25、300，以及 `minAmplitude` 0.01 时的 3）：整数权重与舍入方式与 libvips 的 `gaussblur` 相同，包括其 8 位向量路径、核宽超过 1024 时的整数路径，以及单精度的预乘透明度。
- 方框模糊：对于不含透明通道的图像，`BoxBlur` 与 Pillow 12.1.1 的 `ImageFilter.BoxBlur` 逐字节一致，整数与小数半径均如此（核对了 0.5 至 200，彩色与灰度；测试保留其中 14 个）。
- 与 Pillow 相同的旋转：`Rotate` 配合 `MethodPillow` 与 Pillow 12.1.1 的 `Image.rotate` 逐字节一致（最近邻按 16.16 定点；双线性与双三次按双精度并舍去小数；带透明的图像在这两种插值下按 Pillow 的 `RGBa` 预乘，填充色亦然；`expand`；半圈与正方形图像的四分之一圈直接翻转）：核对了彩色、带透明与灰度图像的 168 次旋转，测试保留其中 84 个。在编译器会融合乘加的处理器上，Pillow 自身的结果可能不同。
- 与 Pillow 相同的变换：`Transform` 与 Pillow 12.1.1 的 `Image.transform`（`AFFINE`、`EXTENT`、`PERSPECTIVE`、`QUAD`）逐字节一致（extent 与 quad 的系数按其 Python 代码计算；最近邻按 `ImagingTransformAffine` 与 `ImagingGenericTransform` 的取法，插值与旋转相同）：核对了彩色、带透明与灰度图像的 141 次变换，其中包括一条线上分母为 0 的透视（这些点按 x86 上的结果视为在图像外），全部保留在测试中。不提供 `MESH`。`TransformPerspectiveQuad` 由四个角算出透视系数（Heckbert 的正方形到四边形映射）：测试中其像素与 Pillow 使用其手册的 `find_coeffs` 以 numpy 求得的系数时相同。
- 灰度：与 Pillow 的 `convert("L")` 逐字节一致，即 `color.RGBToYCbCr` 的亮度；在全部 1677 万种颜色上，与精确的 Rec. 601 亮度最多相差 0.5 级。（`color.GrayModel` 先计算至 16 位再舍去低 8 位，最多相差 0.99 级，且 16% 的颜色未取到最近的一级，故未采用。）
- 色彩调整：与 sharp 0.35（libvips 8.18）的 `modulate` 相比，每个像素相差不超过 1，平均 0.14。
- `Trim`：像素相同时，裁剪范围（大小与位置）与 sharp 0.35 的 `trim` 相同（在带噪点的 JPEG 白边上以阈值 0、3、10、40 核对，并核对了灰尘斑点、带与不带 `LineArt` 的线稿、指定背景色及边距）。
- **与 sharp 相同的缩放**：`ResizeOptions.Method` 设为 `MethodLibvips` 时，`Resize` 与 sharp 的像素逐字节一致。它逐步按 libvips 的缩放以同样的运算进行：先纵向再横向，每个方向各自取整到 8 位；缩小超出 2 倍的部分先以定点方框平均（`vips_shrinkv`、`vips_shrinkh`），其余按 1/64 像素定位、12 位定点权重的核窗口计算（`vips_reducev`、`vips_reduceh`），每个输出位置在每行开头以及纵向每 10 行（sharp 顺序读取时 libvips 在 `vips_reducev` 之后加的缓存的分块）开头重新计算、之后逐个累加；`KernelNearest` 先抽样；放大用 `vips_affine` 的最近邻、双线性或双三次插值（边缘重复）或 `vips_zoom`；与 sharp 一样先以 8 位把颜色乘上 alpha、之后再除回，`FitContain` 给带透明的图像填充的背景色也同样乘、除（图像有缩放时；不缩放时 sharp 直接用原颜色填充）；JPEG 按 sharp 选择的倍数用 libjpeg 的缩放解码在解码时缩小，并按 libvips 裁成 `floor(w/k)` × `floor(h/k)`；配合 `FastShrinkOnLoad` 时 WebP 按 libwebp 的方式在解码时缩放到 libvips 的 `rint(w/s)` × `rint(h/s)`（`use_scaling`：每个平面按每个像素覆盖的面积以 32 位定点平均，有损图像的色度从自身尺寸缩放，两边都缩到四分之三以下时跳过环路滤波，无损图像先把颜色乘上 alpha）。在 sharp 0.35.5（libvips 8.18）上核对了 578 次缩放（全部核；缩小 1.01–40 倍、放大至 3 倍、两者同时；1 像素的边；带透明与灰度；所有 fit 与位置、半透明背景；之前的转向与 EXIF 转向；解码时缩小的 JPEG：4:2:0、4:2:2、渐进 4:4:4 与灰度，2、4、8 倍；有损、带 alpha 的有损与无损 WebP，奇数尺寸，所有 fit 与核），测试保留其中 180 个。WebP 的缩放解码另与 libwebp 的 `dwebp -scale` 核对了 14 个文件、各 7 种尺寸（简单与普通环路滤波，保留与跳过）。16 位图像按 8 位缩放（sharp 保留 16 位）。
- **与 Pillow 相同的缩放**：`ResizeOptions.Method` 设为 `MethodPillow` 时，`Resize` 与 Pillow 的 `Image.resize` 逐字节一致：权重相同（按每个源像素到输出像素中心的距离取滤镜值，缩小时按倍数放宽，归一化后为 22 位定点），两遍处理相同（先横向——只处理第二遍要读的行——再纵向，每遍取整到 8 位），RGBA 与 LA 的预乘相同（`RGBa`、`La`：c·a/255 四舍五入，再按整数除回），最近邻也相同（坐标逐像素累加的仿射缩放）。在 Pillow 12.1.1 上核对了 346 次缩放（全部滤镜；缩小至 30 倍、放大至 3 倍；1 像素的边；RGB、RGBA、L、LA；先转向；`draft` 之后的 JPEG），测试保留其中 57 个。配合 `ReducingGap` 时即 Pillow 的 `Image.thumbnail` 与 `resize(…, reducing_gap=…)`：尺寸按最接近的宽高比取整，JPEG 按框的该倍数 draft 并从 draft 给出的 box 缩放，先做 `Image.reduce`（取滤镜所及的整像素框，每格 `((和 + n/2) · m) >> 24`，`m` 为单精度的 2³²/(256n)）；另核对了 90 个用例（PNG 的 RGB、L、RGBA，基线与渐进 JPEG，全部滤镜，gap 1 至 5.5）。各种 fit 即 `ImageOps.contain`、`cover`、`pad`、`fit`：尺寸与位置按 Python 的四舍六入五成双取整，`fit` 把其小数裁剪框直接缩放到框；另核对了 90 个用例，测试保留其中 32 个。
- **Pillow 的 ImageOps 与 ImageEnhance**：`Posterize`、`Solarize`、`Equalize`、`AutoContrast`（两端截去、忽略的色阶、`PreserveTone`）与 `Enhance`（色彩、对比度、亮度、锐度）与 Pillow 12.1.1 的 `ImageOps.posterize`、`solarize`、`equalize`、`autocontrast` 及 `ImageEnhance` 逐字节一致：查表按 Pillow 的 Python 代码计算（截去比例用 Python 的浮点整除），`Image.blend` 用单精度并舍去小数，平均明度同 `ImageStat`，`SMOOTH` 滤波用单精度且保留边缘像素。核对了 638 个用例（RGB、L、RGBA、噪声图；增强系数 −0.5 至 3.7），测试保留其中 69 个。`Filter`（十种内置滤镜）与使用 `MethodPillow` 的 `Convolve`（`ImageFilter.Kernel`）与 Pillow 的 `im.filter` 逐字节一致，核对了 240 个用例（RGB、L、RGBA、LA、比核还小的图像），测试保留其中 36 个。Pillow 的 `ImageOps` 拒绝带透明的图像，本库则只处理红绿蓝、保留透明度。
- 填满裁剪：居中裁剪的位置与 sharp 相同（多出的一像素归右侧与下方）。`InterestingEntropy` 在像素相同时选出与 libvips smartcrop 相同的裁剪（在四张照片的八种裁剪上核对）；由于本库默认的缩放与 libvips 略有不同，像素以及相近情形下的裁剪可能与 sharp 不同（8 次中 6 次相同）；用 `MethodLibvips` 时像素与 sharp 相同。`InterestingAttention` 按 libvips 的方法实现，并按 libvips 的方式缩小；核对的 6 次全部选出与 sharp 相同的裁剪（像素相同时与 libvips 6 次中 5 次相同）。
- `inspect.Stats`：`Channels`、`Entropy`、`Sharpness` 即 sharp 0.35 的 `stats()` 中的 `channels`、`entropy`、`sharpness`（各通道的值、首次出现位置与总和完全相同，平均值、标准差、熵与锐度一致到 12 位有效数字；在四幅图像上核对，含透明与不含透明的图像及灰度图像）。sharp 的 `dominant` 是 4096 个区间中最满的那个的中点；`Dominant` 列出至多五种颜色，各为其所覆盖像素的平均色。
- 仿照 sharp 0.35 的色阶与滤镜：`Negate`（含与不含 `Alpha`）、`Linear`、`Threshold`（不含透明的图像；含 `PerChannel`）、`Median`、`Convolve` 以及带 `Linear` 的 `Grayscale` 与 sharp 的 `negate`、`linear`、`threshold`（含 `greyscale: false`）、`median`、`convolve`、`greyscale` 逐字节一致；带 `Lightness` 的 `Modulate` 与带 `lightness` 的 `modulate` 相差不超过 1；`CLAHE` 与 `clahe`（libvips 的 `hist_local`）逐字节一致（窗口大于图像时 libvips 报错，本库继续镜像）；`Normalize` 与 `normalise` 相差不超过 1（明度百分位与 libvips 的 `vips_percent` 完全相同：按整数级统计，计数按 `vips_hist_norm` 的方式缩放并截断，取第一个超过该百分比的级）；`Tint` 与 `tint` 相差不超过 1（其灰度与 libvips 的 `B_W` 完全相同）。`Median` 也与 Pillow 的 `MedianFilter` 逐字节一致（含透明通道）。`Composite` 的混合模式在底图不透明时与 sharp 的 `blend` 相差不超过 1（libvips 对乘以透明度后的颜色而非原色套用 PDF 混合公式，本库同样如此，以保持结果一致）；底图透明时，可见部分（按透明度加权后）的颜色相差不超过 3。`Gamma` 采用 ImageMagick `-gamma` 的定义（sharp 的 `gamma` 只作用于缩放前后）。与 sharp 不同，`Threshold` 保留透明度而不对其二值化。`Rotate` 与 sharp 的 `rotate` 逐字节一致（30、60、−17.5、200 度，以及带透明的 45 度）：即按旋转矩阵做 `Affine`，其正弦与余弦按 libvips 所用 C 库的方式正确舍入（Go 的 `math.Sincos` 可能差最后一位，30 度时会让外接框差一个像素）。使用 `MethodLibvips` 的 `Sharpen` 与 sharp 带 sigma 的 `sharpen` 只在 46350 个值中的 1–3 个上相差 1 级（含透明的图像与 sigma 0.6 时逐字节一致）：它逐步按 libvips 的精度走 LabS 换算（线性光查表、单精度的 XYZ、插值的立方根表、舍去小数的 LabS、明度的整数高斯模糊、曲线的 65536 项查表，再换算回来），相差的几级来自 libvips 的立方根——它取自 C 库的 `cbrtf`：在 Windows 上其中 31% 与精确值差最后一位，本库用精确值，其他系统又各不相同。`Affine` 与 sharp 的 `affine` 逐字节一致（默认双线性插值，以及最近邻与双三次插值）（旋转、放大、带背景色的偏移；含透明与不含透明）：输出框相同，源坐标的步进方式相同（在 libvips 每个 128 列的图块起点重新计算），12 位定点权重相同，带透明时单精度预乘也相同。`Dilate`、`Erode` 与 sharp 的 `dilate`、`erode` 逐字节一致（照片、`threshold` 之后、含透明的图像，以及宽于图像的方块）；`Rank` 与 Pillow 的 `RankFilter`、`MinFilter`、`MaxFilter` 逐字节一致。`Recomb`（3×3 与 4×4）与 `Unflatten`（含透明与不含透明的图像，以及在 `Threshold` 之后）与 sharp 的 `recomb`、`unflatten` 逐字节一致；`ExtractChannel` 与 `RemoveAlpha` 给出存储的通道值，与 sharp 的 `extractChannel`、`removeAlpha` 相同。
- 转换至 sRGB：在 Display P3（采样曲线与参数曲线两种表示）和 Adobe RGB（gamma 曲线）三种配置下，与 LittleCMS 的每个值相差不超过 1，约 1.6% 的值相差 1。查找表类配置（lut8、lut16、lutAToB，连接空间为 Lab 或 XYZ，RGB 与 CMYK）按其感知表转换，插值方式与 LittleCMS 相同（四面体插值；四维时沿第一维在两次四面体插值之间线性插值），网格每维 CMYK 17 点、RGB 33 点，与 LittleCMS 优化 8 位转换时相同：CMYK 印刷配置（Windows 的 RSWOP，lut16 至 Lab）在 15900 种颜色上与 LittleCMS 的感知转换相差不超过 1 级（0.7% 有差），各类测试配置相差不超过 1（CMYK）与 3（RGB）。黑点补偿与 LittleCMS（2.17 及 2.20）在感知转换到第 4 版 sRGB 配置时的做法相同（Pillow 的 `ImageCms.createProfile("sRGB")` 与 sharp 的 sRGB 配置都是第 4 版）：配置的黑点（第 4 版感知表为规范规定的固定值；第 2 版取墨量最多或 RGB 为 0 时颜色的明度，作为同明度的中性灰）在 XYZ 中线性映射到 sRGB 的黑，白点不变。不带色彩配置（或配置无法读取）的 CMYK 文件按 libvips 的 CMYK 配置转换（Graeme W. Gill 的 “Chemical proof”，公有领域），与 libvips、sharp 相同：在 16384 种颜色上与 LittleCMS 2.17 相差不超过 1 级（0.9% 有差）。sharp 0.35.5 的结果在暗色处与此最多相差 24 级，原因是其内置的 LittleCMS 2.19 没有把黑点取为中性灰（2.20 已恢复）：若保留黑点原有的色彩，同样的转换与 sharp 相差不超过 1 级。在内存中构造（`FromImage`）、不带配置的 `*image.CMYK` 保持 `color.CMYK` 给出的值。灰度配置（色调曲线，如 Photoshop 的网点扩大配置）把每级灰映射到亮度相同的 sRGB 灰，图像仍为灰度：测试配置与 LittleCMS 结果相同。
- 任意角度旋转：距边缘 2 像素以上的区域，每个像素与 Pillow 的双线性旋转（`expand=True`）相差不超过 1。边缘有意不同：本库将最外一圈像素按覆盖比例与背景混合（与 libvips 相同），边缘平滑；Pillow 为硬边。画布取恰好容纳全图的最小尺寸，三者的计算方式各不相同：将 150×103 旋转 30° 时，本库与 Pillow 得到 182×165，sharp 四舍五入为 181×164（角部会被裁去少许）。
- 所有新操作及各编码器的输出在 x86-64 与 32 位 x86 上逐字节一致；ARM64、PowerPC、s390x、RISC-V、LoongArch、MIPS 由自动测试中的校验值测试核对（浮点运算中每个乘积先取整再相加，以免部分处理器将乘加融合为一条指令而导致结果不同；自动测试会为 ARM64、POWER、s390x、RISC-V、LoongArch 编译本库，编译器若融合了任何一处即失败）。

## 有意的差异

- **GIF 调色板**：标准库将所有非调色板图像一律降为固定的 256 色（Plan 9 调色板），一张照片仅 29dB（SSIMULACRA2 38）。本库默认依据图像内容选色，同一照片可达 40dB（83）；界面截图由 33dB 提高到 65dB，且文件更小。`FixedPalette` 可切换回标准库的方式。动画同样依据全部帧统一选色。颜色比较与误差扩散照 libimagequant（pngquant 的库，sharp 也用它）的做法：在其 gamma 下比较，绿色权重高于红、蓝，过大的误差只传四分之三。与 sharp 0.35（libvips 经 cgif 用 libimagequant 写 GIF，默认力度 7）相比：12 张不同类型的照片缩到 1024×1024 以内，SSIMULACRA2 81.3 对 76.9，butteraugli（3 范数）1.07 对 1.64，文件大 5%；一张平滑照片及其 18 个编辑版本，64.0 对 63.9，1.94 对 2.45，文件小 6%；两张界面截图 93.6、92.4 对 92.6、92.2，文件大小相同。上述平均值未计入：一张 sharp 的 GIF 降到 52 的照片（本库 84），以及一张不超过 256 色、本库原样保留的图画。6000×4000 照片缩到 1536 以内写成 GIF，单核 0.36s，sharp 1.81s（最快的力度 1 为 0.36s）；文件比 sharp 力度 7 的小 11%（比力度 1 的小 19%），得分更高（SSIMULACRA2 61.0 对 59.7）。
- **JPEG 文件**：JPEG 默认按 libjpeg-turbo 的方式写出，因此与 Pillow、sharp 逐字节一致：libjpeg 的颜色转换、4:2:0 与 4:2:2 下采样（舍入偏置横向交替，图像下方的色度重复其最后一行）、精确整数正 DCT、量化的舍入、右边与下边之外的填充块、优化的哈夫曼表（`Optimize`）以及标记（每张表各一个 DQT 与 DHT 段）。Pillow 的文件另有 JFIF 段，本库只在有分辨率时写出；sharp 默认去掉元数据，不写 JFIF，其文件与本库完全相同。核对了 Pillow 12.1.1 写出的 310 个文件（1×1 至 1200×900，质量 1 至 100，4:2:0、4:2:2、4:4:4、灰度、优化哈夫曼表）与 sharp 0.35.5 写出的 96 个；sharp 把灰度图像转成 sRGB 后写成三个分量，本库与 Pillow 一样写成一个。渐进式文件的扫描按 mozjpeg 的方式选择，而非 libjpeg 的简单渐进。本库以前遵循的标准库编码器在颜色转换、DCT 与下采样上有差别，约差一个色阶。 设 `JPEGOptions.OvershootDeringing` 时与 sharp 的 `jpeg({overshootDeringing: true})` 逐字节相同（mozjpeg 的 `preprocess_deringing`，以 float32 移植、不融合运算，各处理器相同，也与 x86-64 上编译的 mozjpeg 相同；在截图与照片 4 档质量共 32 个文件、合成文字/饱和色/噪点的 4:2:0 与 4:4:4 共 18 个文件上核对；被改动的块改走整数变换而非 SIMD，因其 16 位通道可能溢出）。
- **JPEG 像素**：JPEG 文件按 libjpeg-turbo 的默认方式解码，因此与 Pillow、sharp 逐字节一致：其精确整数反 DCT、把下采样色度恢复到全尺寸的“fancy”三角滤波（横向、纵向或两向，行带边界处暂留一行）以及 YCbCr 转 RGB 的查表（在 Pillow 写出的 57 个文件上核对：1×1 至 401×233，各种下采样，基线与渐进，含重启标记；在跨越多个行带的 2001×1501 文件上；以及 Go 自带的 JPEG 测试文件）。标准库使用另一种反 DCT，色度直接重复而不插值，换算的舍入也不同：在一张 4:2:2 照片上，其像素与 libjpeg-turbo 最多相差 23 级（PSNR 39.9 dB），与原图的差距也多 0.36 dB。以下情况不按 libjpeg 的方式换算：编码器不会采用的分量采样方式（Go 测试文件 121121、211211、221122、222112，各分量重复到全尺寸）、CMYK 与 YCCK 文件，以及 `FastShrinkOnLoad`（用 libjpeg 的缩小反 DCT 把各分量的块同等缩小；libjpeg 对 4:2:0 文件的色度只缩小一半）。为 `MethodLibvips` 在解码时缩小的 JPEG 则按 libjpeg-turbo 的缩放解码逐字节一致，也就是 Pillow 的 `draft`（在基线 4:2:0、4:2:2，渐进 4:4:4 与灰度文件上按 2、4、8 倍核对）。JPEG 不经任何操作直接写成 JPEG 或有损 WebP 时，保留文件中原有的 YCbCr：色度不先恢复全尺寸再缩小。
- **有损 WebP 的颜色**：`x/image` 按 JPEG 的取值范围换算 WebP 的亮度与色度，颜色对比度低于 libwebp（浏览器）的结果，平均相差 6–8 个色阶，最大 33；而且每个色度样本直接用于整个 2×2 块，色彩边缘处会出现色块。本库按 libwebp 的方式换算（色度在样本之间插值，采用 libwebp 的整数运算），解码像素与 libwebp（`dwebp`）逐字节相同，已在 `x/image` 的有损文件、奇数尺寸与带透明通道的文件以及一张 1550 万像素的照片上核对。`Metadata()` 对这类文件仍报告 `ycbcr`，即其存储方式。
- **JPEG 压缩的 TIFF**：条带或图块为 JPEG 流的 TIFF 文件（压缩方式 7，即 libtiff 的写法，libvips 与 sharp 默认如此），`x/image` 不支持，本库可以读取：每个块连同各块共用的表（JPEGTables）按 JPEG 解码，支持彩色（YCbCr）与灰度。像素与同样的 JPEG 流作为文件解码所得相同（在带或不带共用表的条带文件，以及 sharp 写出的条带与图块 TIFF 上核对）。 也能写出（`TIFFJPEG`）：条带由整数个块行组成，表放在 JPEGTables，质量低于 90 时 YCbCr 4:2:0、90 起 4:4:4（libvips 从 90 起存 RGB），灰度存灰度；Pillow 解出的像素与本库相同，50 与 80 档的分数与 sharp 的相同（SSIMULACRA2 差不超过 0.05）。色度高度减半时，条带末尾两侧各一行的色度上采样取不到条带另一侧的色度，所有这类 TIFF 都如此（libtiff 逐条带单独解码）。
- **分辨率**：输入记录的分辨率默认写入 JPEG、PNG、TIFF、BMP 输出（JFIF 段、pHYs 块、分辨率标签、文件头字段），标准库不写这些；输入没有分辨率时，JPEG 输出不变（没有 JFIF 段）；调用 `Density(0)` 后所有输出均不变。分辨率的读取方式与 sharp 0.35 相同（在 sharp 写出的 JPEG、PNG、TIFF、WebP 文件上核对，sharp 也能读回本库写出的值）：优先取 EXIF 的，每英寸 25.4 像素及以下视为未记录；按每米或每厘米存储、可由整数 dpi 换算得到的值还原为该整数，sharp 则把所有分辨率都四舍五入为整数。
- **ICC**：输入带有 ICC 色彩配置时默认写入输出，因此此类图像的输出比标准库编码多出 ICC 数据；调用 `StripICC()` 后两者相同。
- 以 JPEG、YCbCr、CMYK 等为来源输出 PNG 时写为 8 位 RGB；`png.Encode` 写为 16 位。
- 基线 JPEG 文件若在一次完整扫描之后再出现扫描（极少见），则予以拒绝。
- 尺寸为 0 的 GIF / BMP / WebP 予以拒绝；标准库返回空图像。
- `x/image` 拒绝读取的 WebP 动画，本库读出其第一帧在画布上的样子：帧位于其位置，画布其余部分透明；帧内像素与该帧码流作为静态图像解码的结果相同。
- JPEG 质量超出 1–100 时返回错误；标准库则静默截断至有效范围。
- 从流（`FromReader`）读取的渐进式 JPEG，其系数以 16 位存储，超出范围（仅见于损坏文件）时返回错误。损坏的渐进式扫描留下未完的块结束游程（EOB run）时，游程随该扫描结束（同 libjpeg，按扫描同步解码需要如此）；标准库会把它带入下一个扫描。
- **含透明通道图像的模糊与锐化**：按预乘透明度计算，透明像素的颜色不会渗入相邻像素；Pillow 对 RGBA 四个通道分别模糊，透明区域的颜色（通常为黑色）会使边缘变暗。

## WebP 编码器

WebP 编码器由本模块自行实现，无标准库可供对照，因此采用两种解码器验证：`x/image` 与 libwebp（通过 Python PIL）的解码结果一致，无损编码可逐像素还原（全透明像素的颜色看不见，设 `WebPOptions.Exact` 时才保留）。与 libwebp 的对比如下（测试环境同[实测](performance.md#实测)）：

- 有损：14 张图（照片、游戏美术图和一张渐变壁纸，6 万至 1550 万像素）分别以质量 45–95 编码、以 libwebp 解码，与 libwebp 1.6（`cwebp`）比较同等 SSIMULACRA2 与同等 butteraugli（3 范数；不超过 600 万像素的 11 张）下的文件大小：

  | 本编码器 | libwebp 默认（method 4） | libwebp method 6 | libwebp 最好设置（method 6、`-af -sharp_yuv`） |
  |---|---|---|---|
  | 力度 5（默认） | 小 6.6% / 9.5% | 小 4.6% / 7.0% | 小 1.3% / 2.2% |
  | 力度 3 | 小 7.1% / 8.5% | 小 4.9% / 5.8% | 小 1.0% / 0.9% |
  | 力度 2 | 小 6.1% / 4.8% | 小 3.6% / 1.4% | 大 0.2% / 2.4% |
  | 力度 1 | 小 4.0% / 1.2% | 小 1.5% / 大 2.2% | 大 2.2% / 5.4% |

  在 11 张界面图、截图与图标（转为 RGB）上，力度 5 在同等 SSIMULACRA2 下与 libwebp 最好设置一样小（比 libwebp 默认设置小 27.4%，libwebp 最好设置为 27.2%；单张从大 4% 到小 11%）。

  相同质量设置下，文件比 libwebp 默认设置的结果小约 2.5%，画质评分更高。一张 3840×2160 照片（PNG 输入）的单线程耗时：力度 1 为 0.43s，力度 2 为 0.54s，力度 3 为 0.79s，力度 5 为 0.99s（8 线程 0.32s）；`cwebp` 默认设置 0.53s，method 6 为 0.81s，最好设置 3.03s。
  - 分段量化移植自 libwebp（按宏块系数的分布将宏块分为 4 段，平坦区域量化较细、纹理区域较粗，强度采用 libwebp 的默认值）。
  - 力度 3 起，颜色按 libwebp 的 sharp YUV 换算：不再对每个 2×2 块的颜色取平均，而是寻找经解码器色度插值后最接近原图的亮度与色度。在细的饱和色线条上，解码图像的亮度（线性光）与原图的差距缩小 3–9dB；对色度插值的解码器（libwebp，因而包括浏览器，以及本模块的解码器）能体现这一改进，不插值的解码器（`x/image`）反而更差。同样从力度 3 起，4×4 块按 libwebp 的方式做网格量化（libwebp 对 16×16 块也做，在此实测文件反而大约 1%）。
  - 力度 5 起，各段的环路滤波强度按 libwebp `-af` 的方法选取：以起始强度为中心，按多种强度滤波重建图像，用 SSIM 衡量后取最佳。
  - 所有力度下，每个色度块直流分量的取整误差都传递给其右侧和下方的块（libwebp 的误差扩散），以消除平滑颜色渐变中的色带。
  - 亮度与色度的量化、率失真权重和环路滤波强度按上述测量（SSIMULACRA2 与 butteraugli）在其中 9 张图上调定，并在全部 14 张图上核验。libwebp 的其他心理视觉项（纹理失真项、量化前提升高频、平坦块惩罚）也试过，没有收益。
- 有损文件的透明通道：按 libwebp 的做法由无损编码器以其默认力度编码（颜色表、LZ77、颜色缓存）：先用快速解析比较「不滤波」与水平滤波（力度 7 起四种滤波都比），取较小者，再用最优解析编码（限 4 百万像素以内的平面；更大的平面上这一步要几秒，力度 7 起才做）；原先只用连续段与上一行复制编码。看不见的透明像素的颜色按 libwebp 的做法（除非设 `WebPOptions.Exact`，即 libwebp 的 `-exact`）尽量省字节：完全透明的 8×8 块压平，部分透明块中透明像素的亮度取平均。透明通道块大小，对比 libwebp 1.6 默认设置与 `-m 6 -alpha_filter best`：一张置于柔和圆形窗口中的照片 8.4KB（22.4KB、7.4KB），一个图标 1.33KB（1.33KB、1.33KB），Tux 3.40KB（3.46KB、3.43KB），一幅图画 3.42KB（3.56KB、3.43KB）；用原先的编码方式分别为 51.8KB、1.91KB、4.98KB、3.61KB。该照片在质量 75 下由原先的 146KB 降为 73KB（libwebp 为 88KB）。编码透明通道时无损编码器最多多用 8MB 内存。 设 ``WebPOptions.AlphaQuality`` 低于 100 时，平面先按 libwebp 的 ``QuantizeLevels`` 降级（照搬移植，级数相同），ALPH 块标明已预处理：6 张图的透明通道块 50 档 35.1KB、20 档 24.2KB（libwebp 36.5KB、23.9KB）。
- 无损：默认级别下，在 17 张截图、照片与游戏美术图上，总量比 libwebp 1.6 最慢的设置（method 6、quality 100）小 5.1%，比其默认设置（method 4）小 5.4%，单核耗时 42s（对方分别为 174s、14s）；单张从大 2.2%（一张截图）到小 8.9%。力度 9（118s）时总量比 libwebp 最慢设置小 5.5%，任何一张最多大 2.1%（同一张截图）。力度 4 也做最优解析，但没有交叉颜色变体与下文其他额外尝试：比默认大 0.6%，耗时为默认的 59%（25s），比 libwebp 默认设置小 4.8%。力度 7 回看远一倍，峰值内存多 2–9MB：总量小 0.3%，单张最多小 0.7%。在 24 张 Kodak 照片上（单核）：默认级别 10.97MB、11.2s，比 libwebp 的 `cwebp -lossless -z 9`（其最慢设置，11.20MB、133s）小 2.1%，比 `cwebp -lossless`（11.34MB、4.3s，含每张图启动程序的时间）小 3.2%；力度 3 为 11.09MB、2.9s，比后者小 2.2%。在 Windows 的 30 张图标与界面图（WebP 2KB 至 36KB）上，比 libwebp 默认设置小 5.0%，比其最慢设置小 0.6%。八线程时（`Threads(8)`；`cwebp -mt`）：17 张图力度 4 用 12.5s，比 cwebp 默认设置（13.1s）小 4.8%；默认级别 21s，对方最慢设置 89s；Kodak 照片力度 4 用 2.3s，比 cwebp 默认设置（4.2s）小 2.4%。与纯 Go 的无损编码器 nativewebp 1.3 的最高压缩级别相比（单核）：本库默认级别在 17 张图上小 23%（对方 19.07MB、15s），Kodak 照片小 7.2%，图标小 31%；力度 1 也更小（8.1% 与 3.3%），耗时为对方的五分之一与五分之三。4 百万像素以内的图另做三件事：一个带 libwebp 交叉颜色变换（不减绿色）的变体参与竞赛，带颜色渐变的图小 2–9%（已编码部分对它估计不准，故竞赛中要领先 3%、最后要领先 1% 才算胜出）；哈夫曼分组也在不用颜色缓存的情况下再做一遍，因为按单组选定的缓存在分组后可能得不偿失（一个图标小 4%）；不带预测的变体还另以只用距离 1 和上一行的贪心匹配（libwebp 的「RLE」引用）编码一遍，小 2% 以上时采用：颜色少的图上，这两种距离的便宜编码胜过在任意处找到的最佳匹配（三个图标小 3–4%）。三者对照片都无益；更大的图上它们会让峰值内存多 2–4MB，后者还会多 40% 耗时。LZ77 匹配按穿过像素的最便宜路径选取（libwebp TraceBackwards 的思路），这需要在每个像素处搜索匹配；各距离上匹配在何处结束会被记住，截图中的长段重复不必一再比较（文件相同，耗时约为三分之一）；在平坦区域，搜索跳过所在连续段内的像素（它们的匹配不会比前一个像素更好），解析也不再从每个像素出发把长匹配逐像素走一遍（图画与透明通道的耗时降为三分之一或更少）。除哈希链找到的匹配外，每个像素处还把最近的上方与左侧各距离（编码最便宜的那些，即 libwebp 的 LZ77「box」搜索的距离）上最长的匹配也交给路径选择：哈希链从最近的像素查起，在平滑区域很少查到上面几行，而那里的残差正重复上面几行（一张渐变蒙版小 16%，Tux 的透明通道小 2%，照片与游戏美术最多小 1%，耗时多 15%）。前缀码的码长按游程友好的方式平滑计数后求得、并省去码末尾的零码长，各自在能使码连同码长更小时采用（两者都是 libwebp 的做法）。哈夫曼分组的块大小试多种取最小；之后把码表开销大于所省的组合并（先合并估计省得最多的一对，同 libwebp 对直方图的贪心合并），再让每块在剩下的组中重新选择（4 百万像素以内的图）：照片小 0.4%，图标小 0.7%，一张图小 1.8%。分组的各轮在每块的符号上进行（由第一轮存下），条件是它们放得进内存预算已到过的峰值以内、且不超过预算的十六分之一（768×512 的照片耗时少六分之一）；否则重读符号流。剩余内存较少时编码器少试几种变换，因此内存上限较低时文件可能更大（一张 400×300 的图：6MB 上限 2384 字节，默认 64MB 时 1914 字节），像素相同。这是唯一一个文件字节随内存上限变化的编码器（经由它，带透明的有损文件的透明通道块亦然）。
- 无损文件中的透明像素：其颜色按 libwebp 不加 `-exact` 时的做法丢掉（`WebPReplaceTransparentPixels`：透明黑；有预测器时取预测出的颜色，即除 alpha 外残差为零），设 `WebPOptions.Exact` 则保留。透明处下有噪点的抠图照片：349KB，精确保留时 477KB（libwebp：367KB 与 492KB）；图标与绘图变化约 1%，有大有小。
- 近无损（`WebPOptions.NearLossless`）：libwebp 的做法，照其 `predictor_enc.c` 移植（`NearLossless`、`NearLosslessComponent`、`MaxDiffsForRow`，每块预测模式按舍入后的残差选，同 `GetBestPredictorForTile`）。它对不用预测器的文件所做的像素预处理（`near_lossless.c`）没有采用：这里总有一个带预测器的候选，旁边还有一个无损候选。每通道误差不超过舍入步长的一半，alpha 为 0 和 255 的不变，同 libwebp。对比 `cwebp -lossless -near_lossless`（libwebp 1.6.0，默认 method 4），23 张照片、截图与游戏美术图：60 档小 7.3%，80 档小 6.6%；单张从大 6.6%（一个 5KB 的图标）到小 13.4%；6 张 Kodak 照片 60 档小 2.9%。单核耗时在照片上约为无损的两倍（1200 万像素照片 8.6 秒对 3.7 秒），libwebp 也要其无损的 2.6 倍。
